## 0. One page for the owner

- **What we build.** Two links, as general Spade libraries that any software can use: a PX4 link (Spade plays the simulator PX4 expects, in lockstep) and an ArduPilot link (Spade plays the physics backend of ArduPilot's JSON interface, in lockstep). Both sit outside the engine; the autopilot is always a separate program.
- **PX4: pin v1.17.0** (the stable release, 13 May 2026, commit `d6f12ad1c4f70ad3230afd7d86e971421e02fef4`, BSD-3-Clause). The simulator (Spade) listens on TCP 4560; PX4 connects. Spade sends sensors (`HIL_SENSOR`, `HIL_GPS`); PX4 answers with motor outputs (`HIL_ACTUATOR_CONTROLS`); Spade steps only after the answer.
- **ArduPilot: pin Copter 4.7.3** (14 Nov 2026, GPL-3.0, phase 5). Spade listens on UDP 9002; ArduPilot sends a servo packet; Spade replies with one JSON object. It does not use MAVLink `HIL_*` at all.
- **MAVLink code: our own small encoder**, tested against reference frames, not the generated headers. Reason in section 3.
- **Running PX4 here: Docker**, not WSL2 (section 4). Docker is already on the box and the leg uses it; the box's WSL distro is Ubuntu 26.04, which PX4 does not list as supported.
- **Download for phase 1** (section 5): PX4 source at the tag, with submodules, plus one build image, about 2 GB for the image and a source clone of a size PX4 does not publish. Nothing is fetched until the lead says.
- **Two things the PX4 pages change from the map.** (1) There is no `none_x500` target: the X500 airframe is Gazebo-only, so the X500 geometry needs our own airframe file (section 1.4). (2) PX4 has no lockstep timeout, so a silent PX4 stalls both sides; the timeout has to live in our link (section 1.3).
- **Effort, my parts** (1 small to 5 large): phase 1 = 4, phase 2 = 2, phase 3 = 2, phase 4 = 2, phase 5 = 3, phase 6 = 3 (section 7).

### 1.3 Lockstep and the missed reply

- **Build-time only.** `BOARD_LOCKSTEP` / `BOARD_NOLOCKSTEP` in Kconfig map to `ENABLE_LOCKSTEP_SCHEDULER`; there is no `SYS_` parameter. [V] `cmake/kconfig.cmake`, `Kconfig`. That the default SITL build is lockstep-on is the docs' statement ("PX4 SITL and the simulators are run in lockstep"); where the default is set was not found **[U]**: the first phase 1 step checks it on the built binary.
- **The sequence** [V, v1.15 docs https://docs.px4.io/v1.15/en/simulation/ ; the v1.17 page dropped the section, the code at v1.17.0 matches it]:
  1. the simulator sends `HIL_SENSOR` with `time_usec`;
  2. on id 0, PX4 sets **its whole clock to `time_usec`** (`px4_clock_settime`), so `time_usec` must only increase; it runs one iteration of estimation and control;
  3. PX4 waits for its other modules (logger, estimator), then sends `HIL_ACTUATOR_CONTROLS`;
  4. the simulator waits for that message, then simulates the physics, then sends the next `HIL_SENSOR`.
  PX4's simulator module blocks at start until the first id-0 `HIL_SENSOR`; PX4 sends its one `HEARTBEAT` first because "without this, we get stuck at px4_poll which waits for a time update". The start is a "freewheeling" period: sensor messages with time run PX4 until it has initialised and answers.
- **A missed reply: PX4 has no timeout and no resend.** Its receive thread prints `poll timeout` about once a wall-second and carries on; its clock advances only from `time_usec`, so it stalls. If our side waits for an actuator message that never comes, both block. [V code, I conclusion] The timeout is therefore ours: **the link waits at most a set wall time (default 5 s, set by the caller) for the reply, then refuses with a named error** (`px4_no_reply`, last `time_usec`, count of sensors sent) and the run ends; it never guesses a reply. The wall-clock wait is I/O only; it never enters Spade's state, so determinism is untouched.
- **Not one reply per sensor by construction.** PX4 sends one `HIL_ACTUATOR_CONTROLS` per `actuator_outputs_sim` update, driven by its control loop, not literally per `HIL_SENSOR` **[I]**. Phase 1's first test measures replies per sensor message over a scripted start and arm; the lockstep rule written in the link is "after each `HIL_SENSOR` with id 0, wait for exactly the next `HIL_ACTUATOR_CONTROLS`", kept only if the measurement shows one per sensor, otherwise changed to what the measurement shows and recorded here.

### 1.5 What the link does each lockstep period

Every period is one sensor period (4 ms by default, a whole number of Spade ticks, which Core's `LockstepHost` enforces at open):

1. `LockstepHost` steps `k` ticks and gives the link the sim time in microseconds and the sensor reads of those ticks (Core: a sample stamped tick k is the state at the end of step k; poll with `since` and refuse on `dropped != 0`).
2. The link converts (section 2) and sends `HIL_SENSOR` (accel, gyro always; baro and mag when those rows exist; their bits set only on their own periods) and, on the GPS period, `HIL_GPS`.
3. It waits for `HIL_ACTUATOR_CONTROLS` (the 1.3 timeout), maps the four motor values to rotor commands (section 2.3) and hands them to `LockstepHost`, which applies them after the board profile's command latency.

Before the first period: listen on 4560, accept PX4's connection, read its `HEARTBEAT` and `COMMAND_LONG`, then run the periods from time 0 (the freewheeling start needs no special code: the first sensor message is the same as any other).

## 2. Frames and the motor mapping (pure functions, tested without any autopilot)

### 2.1 Frames

Spade's design frame is +X forward, +Y up, +Z right, origin on the lower face of the bottom plate; the world is Y-up. PX4 and ArduPilot use NED (world) and FRD (body).

- **Vector, world or body:** (N, E, D) = (X, Z, -Y), and the same for body (F, R, Dn) = (X, Z, -Y). The matrix has determinant +1, a proper rotation: no mirrored axes.
- **Orientation:** quaternion q_body-to-world in Spade becomes q' = R q R^-1 with that same R (a pure change of basis; w unchanged), written (w, x, y, z) as `HIL_STATE_QUATERNION` and JSON `quaternion` want.
- **World heading:** the link's config says which Spade world direction is north and where home is (lat, lon, MSL height of Spade's y = 0). Default: north = world +X, east = world +Z. Position to GPS uses a local-tangent flat-earth approximation about home; the error is below 1 mm at the 1 km scale of our worlds, so it is a documented choice, not a model **[I]**, and the link refuses a body farther than a set range from home.
- **Accelerometer:** specific force in FRD: at rest and level it reads (0, 0, -9.80665). Spade's IMU already gives specific force in the body frame (`engine/sensors/imu.hpp` section 1: level at rest reads +g along +Y up), so this is the same vector through R: (0, 0, -g).
- **Tests (RED first):** each map's determinant; level-at-rest accel = (0, 0, -g); a 90-degree yaw/pitch/roll maps to the expected NED/FRD vector; quaternion round trip; velocity to cm/s rounding and clamp (`int16` limit 327.67 m/s, refused beyond).

### 2.2 `HIL_GPS` from Spade's GNSS row

`GnssSensorSpawn` carries mount, rate, white noise, correlated bias. The link converts position to lat/lon/alt with the home above, velocity to cm/s NED, and sets `fix_type` 3, `satellites_visible` (config, default 10), `eph`/`epv` from the sensor's sigmas (HDOP/VDOP x100, a documented choice). The GNSS row's exact sample fields are confirmed with Core when the code starts **[U]**.

### 2.3 Motor values to rotors

PX4 sends normalized motor values 0..1 (section 1.2), indexed by its motor number (1..4 = channel 0..3). The link owns the map (agreed with Core; it moves to `fc_host` only if the ArduPilot link needs the same inversion):

- **Index table:** an explicit table in the link's config from PX4 motor n to Spade rotor i, **checked at open against the model's rotor positions and spins and the airframe file's `CA_ROTOR` positions and signs**; a mismatch is a named refusal, never a guess. Spade's `fpv_5inch` order is 0 front-right (spin +1), 1 front-left (-1), 2 rear-left (+1), 3 rear-right (-1); PX4's iris and 4001 rotors run front-right, rear-left, front-left, rear-right **[V from the 4001 coordinates, I for the spins]**. The X500's table is made from its model when the code starts.
- **Value to speed:** a linear map from the normalized value to shaft speed, `omega = omega_idle + u (omega_max - omega_idle)`, as PX4's Gazebo motor plugin takes its input **[I]**; the numbers come from Physics' model for the airframe, **chosen so the model's hover command equals the airframe's `MPC_THR_HOVER` (0.60 for the X500)**. Spade's `set_rotor_commands` takes rad/s and is persistent.
- Disarmed outputs are 0 in PX4's message (not the idle speed): the link sends the model's rest command (spin-down by the rotor's own time constant).

## 3. MAVLink code: our own small encoder (recommended)

The choice, from the read pages [V] https://mavlink.io/en/ , https://mavlink.io/en/mavgen_c/ , https://github.com/mavlink/c_library_v2 :

| | Generated C headers (`c_library_v2`, MIT) | Our own encoder |
|---|---|---|
| Licence | MIT (the generated C; the generator, pymavlink/mavgen, is LGPLv3 and never linked) | ours |
| Size | 18.6 MB packed repo; `common/` about 236 files, 6.7 MB, plus `standard/` and `minimal/`; `common.h` alone 381 KB | about 300 lines |
| Pinning | **No tags or releases**; regenerated by a bot on every change ("autogenerated headers for rev ..."); pin by commit SHA | no drift |
| Build | packed structs: the pages note `-Waddress-of-packed-member`, a risk under gcc `-Werror` (our gcc check); MSVC supported | ours, our warnings |
| Coverage | every message, which we do not need | the handful below |

**Recommend our own** (`tools/fc_link/mavlink/`), for a fixed handful of messages: `HEARTBEAT` (0), `COMMAND_LONG` (76), `HIL_SENSOR` (107), `HIL_GPS` (113), `HIL_ACTUATOR_CONTROLS` (93), optionally `HIL_STATE_QUATERNION` (115) for ground truth; the offboard side (`SET_POSITION_TARGET_LOCAL_NED` 84, `ATTITUDE` 30, `LOCAL_POSITION_NED` 32) is added when phase 2 asks, not before. Why: the set is small and fixed; a vendored 7 MB of generated headers in a tree with a third-party notice and a warning problem buys messages we never send; and what a hand-written encoder can get wrong is exactly what a test pins (below). The cost is the field-order and CRC pitfalls, which the tests make visible.

**The wire format** [V] https://mavlink.io/en/guide/serialization.html : v2 frame = `0xFD`, len, incompat flags, compat flags, seq, sysid, compid, msgid (3 bytes), payload, CRC (2 bytes, low first), optional 13-byte signature when incompat flag 0x01 is set; 12 to 280 bytes. Payload fields are sorted by size, largest first (stable for ties, arrays by element size); extension fields are appended in XML order, not reordered; **trailing zero bytes are truncated on send and zero-filled on receive**. CRC is CRC-16/MCRF4XX (init 0xFFFF; check value of "123456789" is 0x6F91) over the header after STX and the payload, then one **CRC_EXTRA** byte per message, computed from the message's name and its non-extension fields in wire order [V description, the type-string details **[I]** from pymavlink]. Traps the tests cover: `HIL_ACTUATOR_CONTROLS` has `flags` (u64) before `controls` on the wire; `HIL_GPS`'s extension `yaw` sits unaligned at offset 37.

| Message | id | CRC_EXTRA | min / max payload |
|---|---|---|---|
| HEARTBEAT | 0 | 50 | 9 / 9 |
| HIL_ACTUATOR_CONTROLS | 93 | 47 | 81 / 81 |
| HIL_SENSOR | 107 | 108 | 64 / 65 |
| HIL_GPS | 113 | 124 | 36 / 39 |
| HIL_STATE_QUATERNION | 115 | 4 | 64 / 64 |
| COMMAND_LONG | 76 | 152 | 33 / 33 |

(from `common.h` of c_library_v2 [V]; CRC_EXTRA depends only on the definition, so it is the same in the `development` dialect PX4 builds **[I]**.)

**How it is tested with no download at test time:**
1. **Known answers in the test:** CRC of "123456789" is 0x6F91; the CRC_EXTRA computed from the field tables equals the table above; lengths and truncation cases.
2. **Golden frames:** frames made once, offline, by the reference (pymavlink, or the generated C headers compiled once), with their exact inputs and the reference's revision, checked in as a fixture; the test compares bytes both ways (encode, and parse then re-encode). PX4's own `requirements.txt` installs pymavlink, so the generator is likely already inside the build image **[I]**; no extra download.
3. **PX4 itself is the end-to-end oracle:** it drops a frame with a bad CRC, so the phase 1 link test cannot pass with a wrong encoder.

Other C++ options, noted: MAVSDK (BSD-3, heavy, PX4-oriented offboard API), mavgen's C++11 output, libmav (runtime XML; licence not checked **[U]**).

## 4. Running the autopilot: Docker (recommended), not WSL2

| | Docker (the leg's tool) | WSL2 |

**Recommend Docker:** build once into a local image `spade-px4-sitl:v1.17.0` from a small Dockerfile in our repo (FROM `px4io/px4-dev@<digest>`, clone at the tag with submodules, copy in our X500 airframe file, `make px4_sitl_default`), and run only that image afterwards. **Do not modify the leg image** (its identity is gated); the alternative of building on `ubuntu:24.04` with PX4's `ubuntu.sh --no-sim-tools --no-nuttx` costs about the same downloads (apt and pip) and drifts. Inside the container the build uses the container's own filesystem, not a Windows mount (PX4's WSL page warns of "very slow execution and access right/permission errors" outside the Linux home; Docker's bind mounts from `C:` have the same cost **[I]**). Docker Desktop itself runs on a WSL2 backend (`docker-desktop`, already there), so the box's resource cap is the same either way. The container is started by one script (`scripts/px4-sitl.ps1`, ours), not by the link library; tests that need PX4 are opt-in and skip when the image is absent (the same pattern as the store tests). QGroundControl is optional and not in the list.

## 6. The ArduPilot link (phase 5; the seam is the same)

Sources [V]: https://ardupilot.org/dev/docs/sitl-with-JSON.html ; `libraries/SITL/examples/JSON/readme.md`, `SIM_JSON.h`, `SIM_JSON.cpp` on github.com/ArduPilot/ardupilot.

- **Transport.** UDP. **Spade (the physics backend) binds UDP 9002 and replies to the address each packet came from**; ArduPilot sends first (the servo packet is the request, the JSON the reply).
- **Servo packet** (ArduPilot to Spade), little-endian, no padding: `{u16 magic = 18458; u16 frame_rate; u32 frame_count; u16 pwm[16]}` = 40 bytes; with 32 channels (`SERVO_32_ENABLE`), magic 29569 and `pwm[32]` = 72 bytes. `pwm` in microseconds (1000 to 2000). `frame_rate` is `SIM_RATE_HZ` (default 400 for copter); `frame_count` rises per frame and resets when SITL restarts (a repeat count means a resend).
- **JSON reply** (Spade to ArduPilot), one object per datagram, newline-framed:
  - required: `timestamp` (absolute seconds), `imu.gyro` (rad/s, body), `imu.accel_body` (m/s2, body; specific force **[I]**), `velocity` (NED m/s), and `position` (NED m from home) or `latitude`/`longitude`/`altitude`;
  - attitude as `attitude` (roll, pitch, yaw rad) or `quaternion` (`q1..q4`); the quaternion wins if both are sent;
  - optional: `rng_1..6`, `velocity_wind`, `windvane`, `airspeed`, `rc.rc_1..12`, `battery.voltage`/`current`, `no_lockstep`, `no_time_sync`.
- **Lockstep.** ArduPilot's time advances **only from the reply's `timestamp`**, and only when `0 < dt < 0.1 s`; a timestamp going backwards is treated as a physics reset; reply exactly once to each servo packet. **A missed reply:** ArduPilot waits (UDP receive timeout 100 ms per attempt) and re-sends the last frame with the same `frame_count`; the readme says after 10 s, the code does it after 1000 ms (a docs/code mismatch). A replied-to resend carrying the same timestamp is harmless **[I]**. Our link applies the same wall-clock rule as PX4's: a configured maximum wait, then a named refusal.
- **Launch.** `sim_vehicle.py -v ArduCopter -f X --model JSON:127.0.0.1` (the readme's example uses `-f octaquad`; `X` is from `vehicleinfo.json` **[I]**). Quad X is `FRAME_CLASS` 1, `FRAME_TYPE` 1; motors in `AP_MotorsMatrix.cpp`: M1 front-right CCW, M2 rear-left CCW, M3 front-left CW, M4 rear-right CW [V]; motor n is `pwm[n-1]` **[I]**.
- **What it means for Spade.** ArduPilot's SITL builds its own GPS, baro and compass from the position we give it; **only the IMU of Spade's sensors reaches the EKF**. PX4's HIL path takes all of Spade's sensor models. That is the technical reason PX4 comes first for "a more accurate simulation".
- **Licence.** ArduPilot is GPL-3.0 [V]. Running it unmodified as its own process and talking to it over UDP is normally separate programs under the FSF's reading ("pipes, sockets and command-line arguments" between separate programs; **[V-sec]**: the GNU FAQ page itself returned 429 and was not retried). Our link implements the documented protocol and **copies none of its code**: `libAP_JSON.cpp` and the JSON structs in `SIM_JSON.h` are GPLv3, and the pybullet example carries no header (the repo's GPLv3 applies); we reimplement from the written spec. Obligations arise only if we **ship** ArduPilot binaries (then GPLv3 for that binary: source offer and licence text). **[I]; not legal advice**; recorded, not enforced (L88c).
- **Release and build.** Copter 4.7.3, 14 Nov 2026 [V] ReleaseNotes (the file lists a 4.7.3-beta1 dated 13 Oct after a 4.7.2 line of 11 Oct, quoted as written). `git clone --recurse-submodules`, `./waf configure --board sitl`, `./waf copter`; Linux and macOS natively, Windows through WSL [V] BUILD.md, https://ardupilot.org/dev/docs/building-setup-windows10.html . There is no official page on running SITL in Docker **[U]**; section 5's preview covers the route.

## 7. Where it lives, the lockstep API, effort

### 7.1 Layout (agreed with Core, 2026-11-21)

- `tools/fc_link/` (mine), outside `engine/`, on Spade's public API only; **`tools/fc_host/` is Core's** (`LockstepHost`: the Simulation loop, the sim clock, command latency, sensor and truth reads; the board-profile reader; the budget model; the run-record writer). **Dependency: `fc_link` to `fc_host` to engine public headers; `fc_host` never includes `fc_link`; `engine/` includes neither.** The link consumes `LockstepHost` and never wraps `Simulation` directly, so the clock, the latency and the run record stay in one place.
- `tools/fc_link/mavlink/` (codec), `frames/` (section 2 pure functions), `px4/` (`Px4Link`), `ardupilot/` (`ArduPilotLink`, phase 5), a thin socket wrapper (Winsock and POSIX; the repo has none today).
- **The seam, mine:** `AutopilotLink` with `open(config)` (listen, accept or wait for the first packet, check the airframe), `exchange(LockstepHost&)` (one period: sensors out, outputs in, command handed to the host), `close()`, and a report (steps, replies per sensor, wall wait, last `time_usec`). Both links implement it, so the run loop and Kat's phase 2 do not know which autopilot is behind it.
- Sensors: IMU and GNSS exist now; **barometer and magnetometer rows are Core's, the models and noise Physics'** (agreed with Core). Until they land the link sends the IMU and GPS bits only.
- **Core's contract for the lockstep period** (from Core's reply): a sensor period is a whole number of ticks (`rate_divider` a multiple of `substeps`), refused at open otherwise; samples are tick-stamped, a sample at tick k is the state at the end of step k (sim time (k+1) dt); the host gives the microsecond stamp (`tick * dt_ns`); poll with `since` and refuse on `dropped != 0` (ring depth 64). Ground truth for the trace: `Simulation::body(BodyRef)` at the same tick.

### 7.2 The autopilot is an input, so a run replays exactly

The link logs every `HIL_ACTUATOR_CONTROLS` value with its tick into the run record. Replaying those values with no PX4 gives the identical Spade trace. That is what makes the phase 1 repeat test honest: Spade's side is exact given the actuator stream; PX4's own logs may differ between runs (threads, wall-clock reads inside PX4), and the report lists any difference instead of hiding it.

**What it proved:** the wire, the CRC, the connection direction (PX4 connects, Spade listens), the TCP channel and the 5 s refusal all work against the real PX4. **What it showed:** PX4 boots ON the lockstep clock, so its modules start only as simulated time advances; until they are up it answers nothing. A link that waits 5 s for the first reply to the first sensor message therefore always loses. The 5 s rule is right once PX4 is running and wrong during boot.

**The boot phase (implemented; `tools/fc_link/px4_link.*`, `Px4LinkConfig::boot_timeout` 120 s and `boot_poll` 10 ms):**

- Until PX4's first HIL_ACTUATOR_CONTROLS the link keeps sending sensor messages at the 4 ms cadence and waits at most `boot_poll` per step. Each such step returns a reply flagged `booting` with zero controls, and is counted in `boot_steps`.
- A backlog of replies delivered with the first one is caught up (`catchup_replies`); it is not counted as a doubled reply. A first reply that is stale with no boot backlog is still `px4_stale_reply`.
- The first reply ends boot. `boot_end_time_usec` is the `time_usec` of that exchange and is Spade's tick 0. From there the link is strict (5 s, `px4_no_reply`). A PX4 that never answers within `boot_timeout` gives "px4_no_reply: PX4 never started ... N boot sensor messages sent".
- Tests: five new `FcLinkPx4` tests on a fake peer (booting and keeps sending; backlog caught up; stale first reply with no backlog refused; never-starts named with its count; 3 boot steps and 300 boot steps give the same world digest). The gate on head `6c4b1b71`: 57 of 57 under `FcLink|FcLive` with the two live tests skipped by design.

**The rule for the host (Spade's side that drives the link, `tools/fc_host`; the lead passes this to Core).** Boot must not leak into the run:
- The host HOLDS its world during boot and builds the boot sensor messages from the held state. It draws no noise from the world's pinned random streams.
- Boot noise comes from a separate fixed-seed stream (the live test uses seed `0x5ADE0000F00D`, the sum of four uniforms), because PX4's validators flag a signal that never changes as stale. Sigmas: accelerometer 0.05 m/s^2, gyro 0.001 rad/s, magnetometer 0.002 gauss, barometer 0.1 hPa. The stream and the sigmas are recorded.
- `boot_steps` and the time offset (`boot_end_time_usec`) go in the run report, the run record and the manifest. The same seed and inputs then give the same world whatever number of boot steps PX4 took (the 3-versus-300 test).

**Two notes for the record.** (1) PX4 segfaults in `simulator_mavlink` when `PX4_SIM_HOSTNAME` does not resolve (PX4's own behaviour, seen while building the start script); the container is therefore always started with `--add-host host.docker.internal:host-gateway`, and the network-off check passes `--network none` with that entry (the name resolves, there is no route, PX4 boots and waits). (2) `scripts/px4-sitl.ps1`: the start creates PX4's log folder in the container; `-Stop` is timestamp-ordered (`docker logs --timestamps`, a stable sort on the prefix), checks every step by exit code, names each failure on a `px4-sitl: -Stop FAILED:` line with exit 7, and takes only a fully qualified run folder (exit 6 otherwise; the container is then left running as evidence). The script test `Px4Sitl.StopReportsItsFailures` (19 cases on a fake docker) is registered next to `FcRun`.

## 14. The exchange seam (phase 1, O140; `tools/fc_link/autopilot_link.*`)

`AutopilotLink::exchange(LockstepHost&)` is the one place where Core's host and an autopilot link meet. The transport is a function (`Px4Transport`: HIL_SENSOR and an optional HIL_GPS in, an `ActuatorReply` out), so the seam is tested against a scripted peer over a real `LockstepHost`, and `Px4Link::exchange` is the real transport.

- **Slices (all built): 1 the IMU, 2 the barometer and magnetometer groups, 3 HIL_GPS.** Slice 1: After boot, one exchange advances the host one IMU period (`advance_to`), takes the IMU sample, converts it with `frames::body_to_frd` and sends HIL_SENSOR (`fields_updated` 0x003F; time_usec = the boot offset plus the sample's time). The reply's four motor outputs go `px4_output_to_duty`, then `autopilot_duties_to_rotor_commands` through the model's chain, and become `host.command()`.
- **Boot.** The first exchange is always a boot message: the host is NOT advanced, the message is built from `boot_readings(step)`, and a `booting` reply only counts a step. The exchange whose reply is the first real one ends boot: `note_boot(steps, time_usec)`, and that reply's outputs are the command before tick 0. From then on `time_usec` continues from that value, so the autopilot's clock never goes back and the boot never reaches the world (the trace hash of a boot of 3 steps and one of 30 is the same; a test pins it).
- **Slice 2.** `baro_binding` and `mag_binding` in the config: a group is marked in `fields_updated` only when its sample is new in the period (mag 0x01C0, baro 0x1A00; with the IMU 0x1BFF), baro in hPa, mag in FRD gauss; a group with no new sample carries its last values; a boot message carries the held pressure and field.
- **Slice 3.** `gnss_binding`, `geo_frame` and `home_world`: a GNSS fix is sent as HIL_GPS in the exchange where it is new (position world to NED about `home_world` to geodetic through `geo_frame`; velocity in NED cm/s with ground speed and course; fix type 3, 10 satellites, HDOP and VDOP 1.0); a boot message carries the held position as a still fix every 200 ms of link time.
- **Next:** the same seam for ArduPilot (phase 5): its wire layer and seam are section 15. A transport refusal (`px4_no_reply` and the rest) comes back unchanged and commands nothing.

## 15. The ArduPilot link's wire layer and seam (built offline; phase 5 still to run)

Built on branch `interface/ardupilot-json` (stacked on `interface/fc-flight`), from section 6's documented layout; nothing of ArduPilot was downloaded, built or run.

- **`tools/fc_link/ardupilot_json.*`** (the wire, pure): `decode_servo_packet` (40 bytes with magic 18458, or 72 bytes with magic 29569, little-endian; a wrong length or magic is refused by name), `encode_state_reply` (one JSON object and a newline: `timestamp`, `imu.gyro`, `imu.accel_body`, `position`, `quaternion`, `velocity`; numbers by `std::to_chars` in fixed format, the shortest text that reads back, so no locale and no exponent; a non-finite value is refused naming the field), `FrameTracker` (a repeated `frame_count` is a resend, a smaller one a restart, a gap is counted) and `ReplyClock` (a new reply's timestamp must be 0 < dt < 0.1 s after the last; dt 0 only for a resend; a refusal changes nothing).
- **`tools/fc_link/ardupilot_link.*`** (the seam): `ArduPilotLink::respond(host, packet)` is one lockstep period. The packet's frame rate must be exactly the IMU's period in ticks (the IMU sample is the frame's gyro and accelerometer: 250 Hz on the flight world's 4 ms IMU; ArduPilot's default 400 Hz would need an IMU every 5 ticks, and is refused naming both); pulses 1 to 4 go through `ardupilot_pwm_to_duty`, the motor map and the propulsion chain to `host.command`; the host advances one period; the reply is the host's time, the IMU sample's gyro and specific force in FRD, and the truth's position, velocity and attitude in NED/FRD. A resend is answered again without stepping; a restart of ArduPilot is refused (the world cannot be rewound). It takes a decoded packet and returns the state to encode: **the UDP loop is section 15.1**.
- **What this does NOT prove.** The golden bytes and the packet layout come from the written documentation (ardupilot.org's SITL JSON page, the JSON example's readme, `SIM_JSON.h` and `SIM_JSON.cpp` as section 6 read them), not from a capture of a real ArduPilot: nothing here shows ArduPilot accepts these bytes, or that `accel_body` is the specific force it expects (section 6 marks that **[I]**), or that its EKF is happy with an IMU-only noise model plus truth for position, velocity and attitude. The first real servo packet and reply come with the phase that runs ArduPilot (a download, a build image, a run: Oversight's and the lead's to OK). Those are the checks to make then: the packet's magic and length against a real one; the reply against ArduPilot's own log of a received JSON frame; whether `frame_rate` 250 is acceptable to it (`SIM_RATE_HZ`), or the IMU period must change.
- **Tests:** `FcLinkArdupilotJson.*` (decoder, encoder goldens, tracker, clock) and `FcLinkArdupilotLink.*` (the seam on a real `LockstepHost` over the flight world: the period, the climb, ignored channels 5 to 16, resend, restart, a frame period that is not the IMU's, determinism, the timestamp rule).

### 15.1 The UDP loop (`tools/fc_link/ardupilot_server.*`)

Built on branch `interface/ardupilot-udp` (stacked on `interface/ardupilot-json`). `ArduPilotServer::serve_one(host)` reads ONE datagram from a `ByteChannel` (`UdpChannel` learns ArduPilot's address from the first datagram and replies there), waiting at most a wall-time timeout (a stall detector: none in time is `io_error` naming `ardupilot_no_packet` and the timeout), decodes it, lets `ArduPilotLink::respond` step the world, and writes one JSON line back. Every refusal comes back unchanged and writes nothing. A report counts packets, replies, resends and bytes. The loop around it is the caller's. Tested over real loopback sockets with a fake ArduPilot in the process.

- **Known gap, not built (nothing uses it yet):** `UdpChannel` binds 127.0.0.1 only. A real ArduPilot in a container reaches Spade through a published or forwarded address (as PX4's TCP 4560 does through `host.docker.internal`), so a bind-on-any-interface option, or the forwarding route, belongs to the phase that runs ArduPilot, with its own network ask.
- **Still unproven, as in section 15:** the packet layout and reply bytes are the documented ones, not a capture; ArduPilot's real behaviour on a missed reply (it re-sends the last frame after 1000 ms by the code, 10 s by the readme) is answered by the resend path here but has not been seen.
