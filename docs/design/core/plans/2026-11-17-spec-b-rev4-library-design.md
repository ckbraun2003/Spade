## 1. Roots, ids, aliases, kinds (E4, E6, E7, C1-C4; K2, K3, K7)

- ROOTS ARE PASSED, NEVER READ FROM THE ENVIRONMENT (E6a): `open_libraries` takes `{name, absolute path}` pairs from its caller, so tests stay hermetic. A helper `parse_library_roots(text)` reads the one text form a host may keep in an environment variable or setting: a JSON array `[{"name": "kat", "path": "C:\\kat\\library"}]`, which has one quoting rule and no separator problem with `:` in Windows paths (E6b). A relative path is refused by name (E6c). A saved project stores root NAMES and ids plus hashes only; paths are per machine, in Settings (E6).
- THE `user` ROOT (E5, K3): not special. It is a root the consumer names, with its own `depends: [default, kat]`; a saved drone and an imported part record go there. Spade hard-codes only the name `default` (and only to say a root of that name is the one Spade ships); `kat` and `user` appear nowhere in Spade's code. Writing into a read-only install is refused by name; which root is writable is the host's setting.
- IDS (C1): `id = kind + "." + stem` with `-` turned into `_` (`world.gate_corridor`, `drone.x500_pliska`, `drone.standard_x250`), the file stem kept as the display `name`. Full form `<root>:<id>`; a bare id is refused.
- ALIASES (C2, K7): a root may carry an alias table in its index, `aliases: {<old string>: <id>}`, which the resolver honours: `mesh:drone/x500-body` resolves to `kat:mesh.drone.x500_body`. The keys are opaque strings (a `mesh:` or `lib:` form is just a string to Spade); the table is data in the root that wants it, so KAT's lives in KAT's root and "resolves forever" is KAT's promise, not engine code. A key that is also an id, or that two roots both claim, is refused by name.
- OPAQUE KINDS (E4, C4): an entry may declare `type: <string>` instead of one of Spade's kinds. Spade lists, finds, hashes and returns the path of such an entry and never interprets its file or its type; a type string is a name KAT chose (recipes, kat.asset.v1, gate sets, bodies, tracks, trajectories, the migrations map, and, since they are KAT-format generator inputs, prefabs, the palette and lighting presets). No KAT type name appears in Spade's code.
- COMPANION FILES (C3): an entry may list `files:` it travels with (a world's `gates.json` and `bodies.json`); the entry hash covers them, so `{id, hash}` misses no gate change. Whether KAT's three flat `*.world.json` lighting worlds are world entries or opaque ones is KAT's choice.
- HASH MISMATCH AND MISSING ROOT (E7, K2): refusals are structured: a stable code plus `{root, path, id}` (`root_not_loaded`, `entry_not_found`, `hash_mismatch`, `alias_conflict`), so the Problems row can say "root 'kat' is not loaded: set its path in Settings > Libraries". A hash mismatch is a warning at `find` (the entry comes back with `hash_matches = false`); KAT's builder warns and offers "accept new hash", and a run or training start whose pinned hash differs is refused by KAT.

## 2. The API: C ABI now, CLI too (S1, E1-E3, E5, E9, E10)

- A `spade_library` C ABI shared library, NOW (E1, E2): JSON text in and out, an opaque handle, loaded with DynLib, deployed beside the exe (an installer row, KAT's). Reads are safe from a worker thread on one handle; `reload(root)` after a write. Output carries a `format` string and a version (S1), so a client refuses an unknown shape by name. Functions: open and close; `list` (rows carry the peek fields in one call: kind or part_kind, mass, category, tags, thumbnail, requires, hash; a `part_kind` filter) (E3); `find` (an entry, its resolved path, `hash_matches`, and for a drone its PARTS MAP as structured data: slot, part id plus hash, placement, so the builder can open a library drone, D165) (E3); `validate` taking TEXT, so unsaved edits validate (E3); `hash`; `resolve` (alias); the write API `add_entry`, `update_entry`, `remove_entry`, each validating before it writes, the only writer of the index YAML (E5); `compose_placement`; `mesh_file_info`; and `compile`: an `AirframeSpec` as JSON in, the `ModelType` as JSON plus a report (stand-in parts, issues) out, refusals as codes (E2). Every function returns the structured refusals of section 1.
- The CLI `spade_library` wraps the same functions and the same JSON, with an explicit locator and no PATH search (S1); it serves the SDK and tests.
- Two panels (E9): Spade Interface's Library panel is Spade's own tool; KAT's Parts and Assets panel is the editor's, built on this API.
- The spec builder (E10) is KAT's: a header-only `dronesim/include/kat/airframe_assembly.h` calls the ABI by DynLib, turns the parts map and library reads into the `AirframeSpec` JSON (placements through `compose_placement`, in a fixed order for the hash) and the report. `compile_airframe` stays Spade's, inside the ABI. KAT sizes that header at about +3 days (theirs).

## 3. provides and limits (K4)

Generic opaque keys of a part record, as in revision 3. KAT derives a drone's capabilities from its parts' `provides`; the KAT behaviour defaults of K4 (rate_loop, envelope, tagged ESTIMATED) are KAT's.

## 4. Compile, the pins, and the rotor block (S2, C5-C7, E8; K1)

- WHAT THE SPADE HOST READS (C5, corrected): identity.name, mass, inertia, drag.mode and coeff, collision_radius, motor.n, arm_x, arm_y, kappa, thrust_per_motor and tau (`scene_config.cpp:190-290`); NOT motor.rotor_omega_max there, which revision 3 listed wrongly (where it is read is unknown). The SDK's rate plant reads more (S2): motor.n, arm_x, arm_y, kappa, thrust_per_motor, rotor_omega_max, drag, identity.name, plus thrust_curve, rate_loop, airspeed_thrust, which stay KAT's. Mass and inertia reach the plant from the host's body state.
- PACKAGES KEEP A FLAT airframe.json (C6, K1): `compile` and `find` give the library drone's compiled physical fields; KAT's package build writes them, with KAT's behaviour fields, into the package's flat airframe.json in today's shape. Nothing of a package is retired by this work; revision 3's step 7 "retiring its copies" is struck. The library drone feeds the Spade host; the package copy flies without the library installed; the byte pin runs at package build, against the package copies.
- GOLDENS (C7): 25 airframe files carry a motor block and fall into FIVE flight sets, one per library drone: competition-700 (14 files, one demo copy lacking rotor_omega_max), crazyflie-2-1 (1), standard_x250 (2), x500-pliska (2), x500 (1); two more sets are Spade render fixtures. The whole-file byte sets (six for competition-700) matter to KAT's own pins and do not move. Components' pin list comes to Core when ready; the goldens live with the `kat` root's tests (KAT's).
- THE FIVE MEASURED DRONES keep their bytes: mass and inertia by fit targets at today's fp32-exact values; positions and spin from slot poses; rotor coefficients and drag carried in a `measured` rotor block.
- THE PARTS-DERIVED ROTOR BLOCK is on the critical path (E8) and moves up the order: it derives arms (the slot poses), kappa, thrust_per_motor, tau and omega_max from the motor and prop parts through the propulsion chain (the ct and cq tables exist), so a user-built drone can fly and show T/W, hover throttle and flight time. A parts-derived drone is a NEW entry with its own goldens; it never replaces a measured one. Sized with Physics.

## 5. What KAT's content needs from Spade (C8, C9, K6)

Runtime kinds KAT needs: presentation mesh, world, drone. Textures: none of the 24 meshes has any, colour only is enough. Prefabs are KAT's `PrefabDef` format, not Spade's, and the palette and lighting presets are used only at generation (the world file is self-contained): so Spade defines NO prefab, material or lighting kinds now (YAGNI); whether its own default library ever wants them is a later call. The presentation mesh needs no new Spade rendering work for KAT (KAT's resolver loads it): Rendering's 3 to 4 days are deferred until Spade's own default library needs palette entries. KAT's tools: `kat_content_author` writes into the kat root through the write API with `generated_from` (recipe id plus hash); `content_harvest` changes paths only; `gen_meshes.py` reads the local store by sha256 and skips when it is absent; KAT repoints `kat_content_refs.py`, `affected_map.py` and about 20 tests (all KAT's).
