## 1. Libraries, roots and ids (Kat's question 1; L88f, L88h)

N ROOTS, NOT TWO. A library root is a folder with a root `library.yaml` holding its `name`, its `library_version` and its entries, and optionally `depends: [<names>]`. Spade ships one, `default` (today's `assets/library`, unmoved; versions 1 and 2 stay valid, the lowest-version rule of CORE-10). KAT's lives in KAT's repo. The consumer names the roots it loads, in order, as `name=path` (a call, a command-line option, or the environment variable `SPADE_LIBRARIES`); there is no installed manifest of other people's libraries and no search path: `open_libraries({{"default", p1}, {"kat", p2}})`.
IDS. A full id is `<root name>:<local id>`; a local id is lower-case, dotted, kind-first, unique inside its root across kinds, stable, never changed by a rename: `default:part.motor.fpv_2306_1700kv`, `default:drone.fpv_5inch`, `kat:drone.x500`, `kat:world.gate_corridor`. (The lead's shorthand `default:fpv_5inch`, `kat:x500` is the display form; the kind prefix is what keeps `drone.x500` and `mesh.x500` apart.) `name` is display only, unique per kind. A bare id with no `<root>:` is refused, never guessed. An id present in two named roots cannot happen (the prefix differs); two roots given the same name are refused.
A KAT ENTRY NAMING A DEFAULT ENTRY: the kat root says `depends: [default]`, and its entries then write `default:...` ids (a kat drone built from default parts: its `requires`, its parts list). The rule is structural: an entry may name only its own root and the roots in its `depends`, cycles are refused, and `default` depends on nothing, so `check_library_contents` refuses any `default` entry that names another root: the general library can never see KAT's content, with no KAT name anywhere in Spade's code.
A ROOT MISSING. A root the consumer names but whose folder or index is absent or unreadable is refused by name at open (`unavailable`, naming the root and the path), never skipped; a `depends` name that is not among the opened roots is refused by name; an id naming a root that was not opened gives a named refusal at `find`, so KAT's saved `{id, hash}` map reports "kat:drone.x500: root 'kat' is not loaded" and the user fixes the path. Nothing is substituted.
ENTRIES, as `library_version: 3` (the root `library.yaml` names per-kind index files: parts, drones, meshes, materials, lighting, prefabs, worlds, so generated content never edits a hand-ordered file): `id`, `name`, `category`, `file`, `tags`, `thumbnail`, `requires` (ids, so a missing prefab mesh is named, not a load failure) and, for generated content, `generated_from: <recipe id + hash>` in the source record so a stale world is detectable without Spade reading the recipe. The extension still decides the kind.
THE HASH is computed, never hand-written: `library_entry_hash(libraries, id)`, the SHA-256 of the entry's file and of the files it names, cached by the loader. KAT's saved parts map stores `{id, hash}` (answer to (9): an airframe references a library drone as is, or an assembly of library parts, by that pair); on a mismatch `find` returns the entry with `hash_matches = false` and KAT chooses warning or refusal. No per-entry versions: a change in meaning is a new id (YAGNI).

## 2. The installed read API and reaching it from the SDK (question 2)

C++ today, in installed `spade::scene`: `load_library`, the typed loaders, `check_library_contents`. Added in one header (`scene/library_api.hpp`): `open_libraries`, `list(kind, filter)` (substring over name, category, tags), `find(id)` returning the entry, its resolved path and a small manifest, named refusals for a missing, wrong-kind or ambiguous id, header-only `peek` per kind (a part's kind and mass, a world's size, so a panel does not load 150 files), `hash`, `validate` (the part blocks, a world, a model: the call the editor Inspector also uses) and `mesh_file_info`; Rendering needs the same lookup to return the resolved path plus the manifest (a mesh's material map, a palette's named list, a lighting) and the hash as a cache key.
For hosts that are not C++: Spade has no extern "C", binding or JSON surface except `spade_geo_fetch --json` and the part-import contract. The SDK (Kat's SDK realm) reaches engine pieces only at run time, through a C ABI shared library loaded with DynLib (or through the Spade host DLL's extensions), and reads JSON files as data; it does not link an engine static library (a rule change for the lead if wanted) and takes no header-only Spade code except per case. So: a `spade_library` C ABI shared library whose functions return JSON text (an opaque handle, no struct layout crosses: list, find, validate, hash, resolve) fits the SDK's existing pattern, and a `spade_library` CLI with the same JSON is the cheaper first step for tools and tests. Interface's estimate: CLI 2 to 3 days, the C ABI 3 to 4 more (the same functions wrapped). The SDK also reads the library's plain YAML and glTF files directly where it only needs data; only `validate`, the hash and compile need Spade's code. The SDK's content paths today read the package's own airframe.json, `content/trajectories/*.csv` and world YAML passed through to the host; none reads meshes.

## 3. Where an imported part's record and file live (question 3)

The FILE (the CAD, and the converted `.spmesh` sidecar) lives in the local store (L88b): a content-addressed folder outside git, named by the host, `<store>/<sha256>/<file>`, the sidecar cached beside it keyed by sha256, converter version, tolerance, unit, axes, scale and object. The RECORD (the part's blocks, mass numbers, install points, citations, the source URL and licence id, the file's sha256) is a part entry in a library root: in the repo for a default Spade ships, or in a user root for a part a person imported. `spade_part_import` writes the file and the sidecar and prints the record skeleton (its JSON-lines result carries it); the editor's Import dialog (KAT or Spade's) writes the record into a user root. The vendored x500 (PX4, BSD-3) and Crazyflie (MIT) sources go to the local store; their records point at them by sha256.

## 4. `provides` and `limits` as generic fields (question 4)

Neither exists in KAT's files yet (Components: no catalogue part file is in the repo; `capabilities` ids come from `capability-namespaces.json`, `limits` is defined nowhere), so Spade defines them. Taken: two optional keys of a part record, validated by form and never interpreted by Spade. `provides`: a list of opaque capability ids (lower-case dotted strings). `limits`: a mapping of opaque names to finite numbers (the unit in the name: `current_max_a`). The engine ignores both, so no drone concept enters the core; KAT reads them. They join the validator's blocks.

## 5. compile_airframe as THE compiler, no mixed motors, and flying bit for bit like today (questions 5, 8; KAT's pin constraint)

`compile_airframe(AirframeSpec)` is the one compiler; KAT builds the spec from its parts map (parts read through the library API, placed with `compose_placement`). MIXED MOTORS: Components confirms none of the five needs them (all n = 4, one scalar thrust_per_motor, kappa, tau and rotor_omega_max, spin alternating on one motor and prop type), so `AirframeSpec` stays at one motor, prop, ESC and battery type and a mixed drone stays refused by name (YAGNI).
WHAT THE SPADE HOST READS of a KAT airframe (Components, `scene_config.cpp:193-285`): identity, mass, inertia, motor (arm offsets, kappa, thrust_per_motor, tau, rotor_omega_max), drag, collision_radius. Everything else (thrust_curve, rate_loop, airspeed_thrust, rate_signs, envelope, capabilities, provenance) is read by KAT's rate-thrust plant, including the SDK's training plant, and stays KAT's: a trained policy's identity includes the airframe bytes it trained on. contact_shape is generated. So the pin that matters to Spade is the compiled ModelType the host hands the sim: mass, inertia diagonal, centre of mass, rotor records, drag, collision radius.
THE FIVE become entries of KAT's library (`kat:drone.*`), built by KAT against Spade's format from the datapack's parts. competition-700 and standard_x250 were measured from a simulator and have no parts, so their parts are the nearest honest ones; x500-pliska is x500 scaled (mass 3.0, T/W 3.7). Reproducing today's flight bit for bit: (1) mass, inertia and the contact proxy are the spec's mass and inertia fit targets set to today's values, which are fp32-exact, so the double composite rounds to the same fp32 and the remainder record absorbs the difference; (2) rotor positions and spin come from the slot poses, exact; (3) the rotor coefficients the host reads (thrust_per_motor, kappa, tau, rotor_omega_max) and drag are CARRIED in the library drone as a `measured` rotor block with provenance (bit-equal by construction), while the parts name the real geometry, mass and look. A parts-DERIVED rotor block (the builder path) is a separate later entry whose pins move with a stated proof (Spec B section 11's tolerances).
THE PIN TEST, in KAT's library tests (the `kat` library is KAT's): KAT dumps the compiled output it produces today for each of the five (the fields above, as the host hands them) as golden data; a test compiles each library drone through Spade's `compile_airframe` and compares every field byte for byte, and fails on any difference. Components notes that the competition-700 package copies (test-racing, test-racing-truth, racing-v3, the VQ1 packages) are DIFFERENT bytes from the library file (sha256 15033e33... vs b19ccbcf...), so the pin is against the package copies that flights and the vq1-bar job read, one golden per distinct byte set; Components is listing them. ## 6. Worlds, prefabs, lighting, materials, meshes, assets, tracks (questions 6, 10)

Per Components: `*.world.yaml` is Spade's format, generated from recipes (the recipe, `kat.asset.v1`, `*.gates.json` `kat.gate_set.v3/v4/v5`, `bodies.json`, `tracks/*.track.json`, the trajectory CSVs and the migrations map are KAT's: the gate set is read by the Spade host and KAT's course reader and its owner is unsure, so it stays KAT's data in KAT's library); prefabs are parametric SDF programs expanded in `dronesim/spade/tools/prefabs.cpp`, engine-shaped; materials become the world file's `materials:` block; lighting presets equal `LightingDesc`. Under L88h all of KAT's go into KAT's own library (KAT's migration, against Spade's format and tools); Spade holds only what is general, in `default`, and provides the KINDS and the tools.
What Spade adds so KAT's library can express them: entry kinds `*.materials.yaml` (a named palette of `MaterialDesc {name, base_color, shading}`), `*.lighting.yaml` (`LightingDesc`), a world entry (`*.world.yaml`), a prefab entry (an SDF program file, if the format is Spade's; PENDING confirm it is the engine's SDF), and a presentation-mesh entry: a `.gltf` plus a map from the file's material name to a palette name, resolved when placed, NOT through `.spmesh` and the solid gate (a presentation mesh has no inertia and no flow wall; Rendering: the glTF reader `render/gltf.cpp` is test-only today and must also read `materials[].name`). Render side, colour-only: 3 to 4 days (Rendering). Textures: Spade's renderer has none (no UVs, no texture store), 5 to 8 days and a clear case first; PENDING Components: does any of the 24 meshes need a texture to read?
(10) A scene picks a world and a track by `{id, hash}` from KAT's library (today a `lib:` path; `resolveSceneRef` has no search path or fallback, so the move is a change of reference form and of 240 files that name a content path: 142 tests, 61 code or build files, 54 fixtures, 16 docs, plus 13 scenes, 6 with `lib:` refs and 47 packages). A scene's saved airframe is already a project-relative copy (`airframe_ref`), not a `lib:` ref.
`kat_content_author` (recipe, prefabs, asset in; world, gates, track out) and `content_harvest` and `gen_meshes.py` are KAT's tools and move with KAT's library; they write into KAT's library root through Spade's library API and format. Spade replaces none of them.
