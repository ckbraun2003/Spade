# Realistic-looking drones (Task L7) -- Core's draft plan (2026-10-26)

> APPROVED by the lead, 2026-10-26 (its rulings are below, under "Rulings"). Drafted for the lead as a draft; the file keeps its name. Expands Task L7 of `docs/design/core/plans/2026-10-21-default-drone-library-plan.md` (lines 226-260) under the lead's rulings 1-5 (2026-10-21; ruling 4, the spinning props, 2026-10-26). Drafted read-only at master `aaacb95`. Each task branches from master when it starts. Nothing here is built.

**Goal.** The six library drones look like drones: a rounded body shell, capped arm tubes, motor bells and lofted propellers. Every mesh is generated by our own code from published dimensions and the L4a blade stations, never from downloaded CAD. The props spin visibly at their rotor's omega in the editor's Run, the airflow drone box and flow_movie. That is visual only: nothing is read back into the sim.

**Architecture.**
- **Generators in `engine/world/mesh_shapes.{hpp,cpp}`** (new; world/ is Core's realm). They are plain functions from numbers to `make_mesh()`: a rounded box, a capped tube, a motor bell (a lathe) and a lofted prop in two hands. Circles and pitch angles use `math::sin32`/`math::cos32`. Everything else is double `+ - * /` and `sqrt` (TD-3).
- **Rigid meshes are the parts themselves** (ruling 1). The body and arms become mesh records (`GeometrySource::mesh`) whose density is the L5 mass / the mesh volume. The motor bells come from a new `AirframeSpec::motor_mesh`, whose mass stays `MotorBlock.mass`. They are drawn and they are the airflow solids.
- **Props are massless rotor parts** (rulings 1 and 3): a new `AirframeSpec::rotor_parts`. Each record names its rotor and a hub-frame mount and has no mass field, so the prop's mass stays `PropBlock.mass` and nothing is counted twice. The compile emits each as a `PartDesc` with `attach: rotor`. `PartFilter::rigid_only` already drops those parts from every solid.
- **The opposite hand is its own mesh** (ruling 5). The generator mirrors z -> -z and re-winds every triangle, so the mesh still faces outward.
- **Goldens** are `.spmesh` sidecars (B5's format) beside each model file, written by the generator under `SPADE_LIBRARY_WRITE` like the model and part files. The model file names each one as `shape: {mesh: {file, hash}}`, so the format does not change (ruling 1).
- **Spinning** uses Physics' P11 azimuth, integrated on the host and passed to `posed_parts()`, which already turns a rotor part by `R_y(s_k psi_k)`.

**Tech stack.** C++23, GoogleTest through ctest, MSVC + Ninja, gcc-13 on the leg. No new dependency, no kernel, binding or Slang change, and no model-file or scene-file format change. One save-format bump (LiveRun's, L7c2) is Interface's and Physics'.

- **TD-3 and M1B.** Nothing new under `engine/` uses libm or a wall clock. `sin32`/`cos32` are only called on [0, 2 pi] (exhaustively tested, `core/fp32_math.hpp:152-198`) and on |beta| < pi/2. Run `BitPortability*:M1B*` before every leg.

## Review Focus

1. **A prop counted as mass or as a solid.** Adding props must leave the model's mass, inertia, drag and `model_identity` bit for bit, and `rigid_only`, LiveRun and `AirflowSolids` see the same parts.
2. **The wrong hand on a hub.** On a +1 rotor a blade's leading edge must lead its turn. The mirrored mesh is outward (volume > 0) and is exactly the mirror image.
3. **A mesh that tilts the axes or moves the mass.** `design_to_principal` stays the identity, the mass is the L5 float, the hover checks still pass, and any inertia shift is named.
4. **libm, a wall clock, or a toolchain difference in a generator.** The scans and pinned hashes must hold, and the gcc leg must reproduce them.
5. **A thin feature or a narrow gap in a solid.** The library solids check at 4 mm must show every part a wall, with no leak and no sheet.
6. **The drag silently changing** when the estimate is refused. The frozen estimate must be bit for bit (Q3).
7. **A library drone the editor can no longer place.** L7b0 merges before L7b2.
8. **The azimuth leaking into the sim.** The step output and digest must be unchanged with psi advancing.
9. **A sidecar mangled as text.** `*.spmesh binary` must be in `.gitattributes`.

## Task L7a: The mesh generators

**Files (Core):**
- create `engine/world/mesh_shapes.{hpp,cpp}`;
- create `tests/test_mesh_shapes.cpp`.

**Cross-realm:** `engine/CMakeLists.txt` (one source line; lead's grant) and `tests/CMakeLists.txt` (standing grant; named in READY).

**API (all names proposed).** Each function returns `Result<GeneratedMesh>`, which is `{std::shared_ptr<const TriangleMesh> mesh; float min_feature;}`. The positions are metres and pass through `make_mesh(..., name)`. The functions are:
- `rounded_box(glm::dvec3 size, double edge_radius, uint32_t segments)`: centred at the origin, extents exactly `size`, every edge and corner rounded at `edge_radius`. `min_feature` is the smallest extent.
- `capped_tube(double radius, double length, uint32_t segments)`: along +Y, centred, with hemispherical caps. `length` is cap centre to cap centre. `min_feature` is 2 radius.
- `motor_bell(double radius, double height, double chamfer, uint32_t segments)`: a lathe in the HUB frame, with its top face at y = 0 (the rotor plane) and its base at y = -height. `min_feature` is min(2 radius, height).
- `prop(const PropMeshSpec&, PropHand)`. `PropMeshSpec` holds the diameter, the blade count, the r/R, c/R and beta stations, the hub cut-out, the section (camber, thickness at root and tip, chordwise points), and the hub gap. `PropHand` is `{ccw, cw}`: ccw goes on spin_dir +1, which turns right-handed about +Y (counter-clockwise seen from the thrust side), and cw goes on -1. The mesh is in the hub frame with the disc plane at y = 0 and blade 0 along +X at psi = 0. `min_feature` is the thinnest section's thickness. A prop is never a solid.

**The construction.**
- **Welded by construction.** Seams reuse their first vertex, and each pole is a single vertex.
- **Circles.** Each circle uses angles `2 pi k / n` through `sin32`/`cos32`.
- **Rounded box.** A face grid whose lines meet the start of each rounding. Each point is projected as `inner + rho * normalize(p - inner)`, which uses sqrt only.
- **Prop sections.**
  - The section is NACA 4-digit-style, with its thickness applied normal to the chord line (no atan).
  - It has a blunt trailing edge of max(1% c, 0.1 mm), so no two surfaces meet at a knife edge.
  - It is pitched by beta about the quarter chord, and the quarter-chord line runs straight along the radius (no sweep or rake).
  - Root and tip caps are strips that pair the upper and lower points at equal x.
- **Prop hub and blades.** The hub is a disc of radius `hub_cutout R - gap`, its own shell. The blades start at `hub_cutout R`. `make_mesh()` refuses touching shells, so a hairline gap (0.5 mm, assumed) separates them. A blade sunk into the hub would be a self-intersection.
- **The cw hand** is the ccw mesh with z negated and each triangle's last two indices swapped.

- [ ] **RED** (`tests/test_mesh_shapes.cpp`, suite `MeshShapes`):
  - `EachShapeIsAClosedOutwardMeshThatMakeMeshAccepts`: shells are 1, 1, 1 and blades + 1, and every volume is > 0.
  - `TheRoundedBoxKeepsItsExtentsAndRoundsEveryEdge`: the bounds equal `size` exactly, a corner sits at its rounding radius, and the volume lies between the box's and the box less its corner cuts.
  - `TheCappedTubeSpansItsLengthPlusItsCaps`.
  - `TheMotorBellSitsBelowTheRotorPlane`: max y is 0 and min y is -height, both exact.
  - `ThePropFollowsItsBladeStations`: at each station the section's chord is c/R x R and its pitch is beta, both within fp32 rounding; the tip reaches R; and no vertex lies inside the hub gap.
  - `ACcwBladeLeadsWithItsSpin`: at psi = 0, blade 0's leading edge is on its -z side and above its trailing edge. That is the side a +psi turn about +Y moves toward (`part_pose.hpp:15`).
  - `TheCwHandIsTheCcwMirroredAndReWound`: positions are (x, y, -z) bit for bit, each triangle is reversed, the volumes are equal, and `make_mesh()` accepts it.
  - `ABadSpecIsRefusedByName`: an edge radius over half the smallest extent; fewer than 3 segments; c/R <= 0; stations not increasing; zero blades.
  - `TheShapesHashesArePinned`: one spec per shape, `content_hash()` pinned from MSVC. **The leg reproduces it** (TD-12).

## Task L7c2: The props spin (P11 merged at `97ddfdd`)

**Files:** other realms' files only (see the table). Core writes no code here. Its part is this spec and the review of each branch against the posing rule.

> **Re-anchored at master `ae73c7c` (2026-10-27)**, after T3, G1 and L7c1. P11 is `engine/physics/blade_azimuth.hpp`: `advance_blade_azimuth(float& psi, float omega, float h)` and `advance_blade_azimuths(std::span<float> psi, std::span<const vehicles::RotorRow> rows, float h)`, which skips a disabled row.

**The posing rule (what Core reviews against).**
- One psi per rotor, in the model's rotor order, in [0, 2 pi), starting at 0 (the authored pose).
- Advanced once per step, after the step, by `advance_blade_azimuths()` with the rows as the step left them: omega after the step, and a disabled rotor holds. There is no other rule and no copy of it (TD-9).
- Passed to `posed_parts()` unsigned, since it applies s_k. The same caller passes the rows' omegas as `rotor_omega`.
- Drawn only. Nothing reads psi back into the sim: no registered state, no `RotorRow` field, no digest input.
- A refusal (false) never fails a step, because psi is only drawn. The refused rotor holds, and the owner surfaces it once: EditorRun on the status line, LiveRun through an accessor the host can show. A stepping sim should never produce one.

**The changes, by owner.**
- **Interface: the draw helper.** `append_vehicle_parts()` (`sandbox/vehicle_draw.hpp:106-115`) gains an overload that takes `rotor_omega` and `psi` spans in rotor order and passes them to `posed_parts()`. ## What P11 needs from Physics

`posed_parts()` already takes psi and turns a rotor part by `R_y(s_k psi_k)` with `sin32`/`cos32` (`part_pose.cpp:114-115`). L7c2 needs only an azimuth to pass, so P11 has to give:

1. **One rule, one function (TD-9):** `psi <- wrap(psi + Omega h)` per rotor. Physics says:
   - which Omega it uses (the row's value before or after the step; P4 needs the one its forces used);
   - whether it accumulates in float or double;
   - the wrap into [0, 2 pi), which must subtract a pinned float 2 pi rather than call `fmod`. That keeps `sin32` in its 1-ulp domain, which `part_pose.hpp:39-41` leaves to the caller.
   It uses `+ - *` only and no wall clock, and it is callable from the host.
2. **The sign.** Psi grows with Omega >= 0 whatever the hand, and `posed_parts()` applies `s_k`. Physics confirms that P4's actuator line uses this same (psi, s_k) convention, so a drawn blade and P4's line coincide.
3. **Its home and form.** P11 says the array is "declared by the airflow module". The editor's Run is a plain `Simulation` without that module, so it needs the same function held on the host, outside registered state, with nothing read back. Physics confirms that this is P11's intended form ("outside RotorRow, so every existing golden holds").
4. **LiveRun.**
   - `blade_azimuth()` returns one value per rotor and is advanced in `step()` by the same function.
   - It starts at 0, which is the authored pose.
   - It is saved and restored, so a resumed film's props do not jump. That bumps `kLiveRunSaveVersion` from 2 to 3 (`live_run.hpp:70`). This is shared with Interface (I1).
5. **What P11 does not need:** any posing change, a format change, registered state, or a GPU mirror. Those are for P4/P5 later.
