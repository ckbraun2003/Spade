# The simulated flight computer and the lockstep host: Core's section (phase 0)

Core, 2026-11-21. DRAFT for the lead; docs only, no code. Owner's word O140: "Let's get spade the work it needs to be able to create a more accurate simulation with compute parts and the px4/ardupilot connects." The map is `Oversight/.agents/plans/2026-11-21-full-sim-flight-computer.md` (phases 0 to 6). Interface writes the link half (`docs/design/interface/plans/2026-11-21-fc-links.md`); Physics the sensor models. What Core and Interface agreed is in section 1. ## 0. The one-page summary

- **Outside the core, in `tools/`.** Two new trees, neither linked into `engine/` (L7): `tools/fc_host/` (Core: the lockstep host, the board profile, the budget model, the measured-mode launcher, the run record) and `tools/fc_link/` (Interface: MAVLink codec, the PX4 link, the ArduPilot link). The engine gains only the barometer and the magnetometer, as sensor kinds (Core plumbing, Physics models), because a sensor has to synthesize inside the step.
- **The lockstep API needs no new engine call and no C ABI.** `step`, `poll_imu`/`poll_gnss`, `set_rotor_commands` and `body()` are enough, on one rule: **every sensor period is a whole number of ticks**. The host owns the clock (`sim_time_ns = tick * dt_ns`).
- **A flight computer is data plus a host-side model.** A board profile (cores, clock, memory, link, a speed factor with provenance; a flight-controller profile adds loop rates and an output latency). **Budget mode** turns declared per-tick costs into command latency and counted overruns, with integers and no clock, so the same seed gives the same result (grade `reference`). **Measured mode** runs the software under test in a Windows Job Object on real time (grade `best-effort`), reported as measured with the box and tree.
- **The run record's strong claim is replay.** The host records the command stream it actually applied. Replaying it without the autopilot reproduces Spade's trace bit for bit. A live re-run is only as repeatable as the software under test, so the repeat test lists differences instead of assuming none.
- **Two things I would change in the lead's picks** (section 6): the barometer and the magnetometer are a **phase 1** blocker, not a phase 4 extra, because PX4's preflight checks want both; and measured mode waits until budget mode has proved itself in phase 2.

Rules. `fc_link` includes `fc_host`; `fc_host` never includes `fc_link`; `engine/` includes neither and knows nothing of MAVLink, PX4, boards or companion computers. `fc_host` is general: its `Link` seam takes any software under test that can be driven as "sensor samples in, rotor commands out" (the PX4 and ArduPilot links are its first two implementations). A board profile (cores, clock, memory) is a domain description, which is why it lives in `tools/` and not in the engine (L7); the engine's part-blocks reader ignores a key it does not own, so a part file may point to a profile without Core's engine code reading it.

Agreed with Interface (their `LinkHost` is fc_host's `LockstepHost`): the link consumes the host and never wraps `Simulation` itself, so the clock, the command latency and the run record stay in one place. The motor mapping (normalized 0..1 to rad/s) stays in the link until a second link needs the same inversion; then it moves to a shared `fc_host` helper.

## 2. The lockstep API

### 2.1 What a link calls

`LockstepHost` is C++, in-process, built against the same public headers a consumer such as KAT uses (KAT's `host.cpp` already drives `Simulation` that way). Calls, as a contract and not as a signature:

| Call | Does | Refuses / reports |
|---|---|---|
| `open(sim, vehicle, sensors, profile, mode, options)` | binds one vehicle and its sensor refs; reads `dt_ns`, `substeps`, each sensor's `rate_divider`; fixes the sensor periods | a sensor period that is not a whole number of ticks (named), a GNSS or baro period that is not a whole number of the IMU period, a profile loop rate the periods cannot serve, `min_grade` not met (section 3.5) |
| `sim_time_ns()` | `tick() * dt_ns`, the one clock | |
| `advance_to(t_ns)` | steps tick by tick to `t_ns` (a tick boundary at or after now); before every tick it releases the commands whose release time has come | `t_ns` off a boundary or in the past; a poll that dropped samples |
| `take_sensors()` | every new sample of every bound sensor since the last call, in index order, each with its time in nanoseconds | `dropped != 0` is refused, never hidden (the ring is 64 deep) |
| `truth()` | `Simulation::body()`: position, velocity, orientation, body rate, at the current tick | |
| `command(omega)` | queues a rotor command (rad/s per rotor) with the latency the mode assigns (section 3) | wrong count, non-finite, negative |
| `counters()` | overruns, late and skipped samples, latency statistics | |
| `close()` | writes the run record (section 4) | |

A sample stamped tick `k` is the state at the end of step `k`, so its time is `(k + 1) * dt_ns`. The stamp holds the tick only (no substep), which is why a sub-tick period is refused: two samples would share one stamp.

### 2.2 How the step relates to the autopilot's period

Reading from the two simulator interfaces (section 6) and from Physics: PX4's simulator link sends one HIL_SENSOR per lockstep step at about 250 Hz (a 4 ms period), with the GPS about 10 Hz; ArduPilot's JSON interface runs at the rate the simulator chooses, 400 Hz by default (2.5 ms; one report saw 1200 Hz, unconfirmed). So the world's tick must divide every period it serves. **Physics proposes `dt` = 500 us with 1 substep**, which divides 4 ms (8 ticks), 2.5 ms (5), 2 ms and 1 ms; 1 ms does not divide 2.5 ms, so it is not chosen. That is a proposal until Physics' phase 1 convergence check (500 us against 250 us on the X500's hover and an attitude step) has run. The fluid and line steps (25 us to 0.2 ms in the film boxes) are a separate loop, off the autopilot path; the lockstep host uses the rigid-body step only.

| Autopilot period `P` | Needs | With `dt` 500 us, 1 substep |
|---|---|---|
| PX4 4 ms | `dt_ns` divides 4 ms | IMU `rate_divider` 8 |
| ArduPilot 2.5 ms (400 Hz) | `dt_ns` divides 2.5 ms | `rate_divider` 5 |
| baro 50 Hz, mag 100 Hz (Physics' defaults, `assumed`) | a whole number of IMU periods | 5 and 2 IMU periods at 4 ms |
| GNSS 100 ms | a whole number of IMU periods (25 at 4 ms) | a GNSS `rate_divider` of 200 |

`rate_divider` is any positive integer in substeps; the host's only rule is that each resulting period is a whole number of ticks.

One lockstep cycle: `advance_to(now + P)` (k ticks), `take_sensors()`, hand the samples to the link, the link sends, the autopilot's reply goes to `command()`. Physics gave the physics side (above). If a model needs a `dt` that divides none of these periods, the host refuses at `open`, and the fix is a different `dt` or a different autopilot rate, not an interpolation inside the host.

### 2.3 The clock across a reset

The autopilot sees `sim_time_ns`. It must never go backwards: after `restore()` or an episode `reseed()`, the host keeps an offset so the time sent stays monotonic, or the link restarts the autopilot (Interface and Core decide; section 6, question 5).

### 2.4 Does the C ABI need anything?

No, for phases 1 to 5. Spade has no simulation C ABI today (the existing one, `spade_library`, is the JSON library ABI), and none is needed: `fc_host` and `fc_link` are C++ against the same installed headers, in process. "Any software under test" is carried by the `Link` seam, the software's own protocol being MAVLink or JSON over a socket, not Spade's ABI. A C ABI to `LockstepHost` is worth building only when a host in another language must drive the world itself. That stays a separate decision, and the camera C ABI (3.3) stays on hold.

## 3. The flight computer as a general vehicle part

### 3.1 The board profile

A profile is one YAML file, `board_version: 1`, read by one function in `tools/fc_host/board` that refuses an unknown key by its path (as the part-blocks reader does). A drone's part file carries `compute: {board: <id>}` to say which part is the computer; the part's mass and pose go through the normal parts path (`compile_drone`, unchanged), and the profile is the one place the compute numbers live.

```yaml
board_version: 1
id: board.rpi5_8gb
kind: companion            # companion | flight_controller | host
cpu:     {cores: 4, clock_hz: 2.4e9, isa: aarch64, grade: published, source: "..."}
memory:  {bytes: 8589934592, grade: published, source: "..."}
link:                      # the path to the autopilot
  type: uart               # uart | ethernet | usb | loopback
  rate_bps: 921600
  fixed_latency_ns: 300000
  grade: assumed
  source: "..."
speed:                     # the board against the box the costs were taken on
  factor: 0.35             # work per second here / work per second there; 1.0 = the same
  reference: {box: "pc-baseline", benchmark: "fc_bench v1"}
  grade: assumed           # becomes measured in phase 6, from one run on the board
  source: "published Geekbench-class ratio until the board runs fc_bench"
```

A `flight_controller` profile records **loop rates only** and adds an output latency:

```yaml
loops:   {imu_hz: 1000, attitude_hz: 250, rate_hz: 1000, output_hz: 400}
output_latency_ns: {value: 1500000, grade: assumed, source: "..."}
```

The autopilot runs at PC speed in SITL, so its own compute is not modelled and the run report says so. The two additions are what the host can still do honestly: commands change only at `output_hz` (a zero-order hold), and a declared, graded `output_latency_ns` stands for the real controller's sensor-to-output delay (a few ms on a Pixhawk-class board), so the loop is not optimistic by that much without anyone seeing it. The grades are the library's five (`measured`, `published`, `retailer`, `derived`, `assumed`), one per group, printed in the run report.

### 3.2 Budget mode: deterministic

Every figure is an integer number of nanoseconds. Nothing in it reads a clock, so the same seed gives the same result.

1. **Costs.** The software under test declares a chain of **stages** in a profile of its own (`costs.yaml`): each stage lists components with `cost_ns` per call **on the reference box**, and the stages run in order (components of one stage run in parallel, on distinct cores). On the board a component takes `cost_ns / speed.factor`. A stage takes the longest of its components; a stage with more components than cores is refused in v1 (no oversubscription model). The chain's latency `L` is the sum of its stages plus the link's `fixed_latency_ns` and `8 * bytes / rate_bps` each way.
2. **Where the costs come from** (software Spade does not own, so Spade cannot read them out of it):
   - **declared**, by the author, with a grade (`assumed` or `published`); or
   - **measured once, then frozen**: a calibration tool (`fc_host_calibrate`, the only place in `fc_host` that reads a monotonic clock) runs the component on the reference box, takes a stated statistic (default p99) over N calls, and writes `costs.yaml` with the box, the tree commit, the date, N and the statistic. A budget run reads only the frozen file and records its hash. Re-measuring is a new file with a new hash, never an update in place.
3. **Latency.** A sample due at `t` is delivered; the command it produces is released at `t + L` rounded up to the next tick (and to the next `output_hz` slot). The command is the previous one until then.
4. **Overrun.** If `L` exceeds the stage's deadline (default: the sensor period), that is a counted overrun, and the host does not deliver the samples that arrived while the chain was busy: it delivers the newest at release time, and the skipped ones count as dropped samples (the poll's own `dropped` idea). A board that is too slow therefore shows a lower effective control rate, a higher latency and a counted overrun, and the software under test sees stale data through its own timestamps, so its failsafe can trip honestly.
5. **State.** The pending-command queue and the counters belong to the host, not to the engine (L7); the host writes them with its own checkpoint (section 6, question 4).

Limit, stated once: a cost is a constant per call. Software whose cost depends on its input (a planner) gets its worst case or p99, and the run report says so.

### 3.3 Measured mode

The software under test runs as its own process inside a **Windows Job Object** that the host creates: a hard CPU-rate cap (`JOBOBJECT_CPU_RATE_CONTROL_INFORMATION`), an affinity mask, a job memory limit (`JOBOBJECT_EXTENDED_LIMIT_INFORMATION`), kill on close. The host paces the world on real time (a monotonic clock read in `fc_host` only; the engine still reads none, L1) and applies each command at the first tick after it arrives. Results vary a little between runs and are reported as **measured, with the box and the tree** they came from.

- A memory cap below the process's peak gives a **named refusal**: the host reads the job's peak usage and the exit reason and reports `memory_cap_exceeded` with both figures, not a crash.
- The commands the host applied are recorded with their ticks, so a measured run still replays exactly (section 4).
- Only the software in the job is capped. PX4 or ArduPilot in WSL2 or Docker is a different process tree and runs at PC speed, as the map says.
- **The honest limit.** A PC cannot run at a board's clock. Caps approximate a smaller machine; caches, the instruction set, memory bandwidth, SMT siblings, thermal throttling and the scheduler's slice length differ, and the cap is enforced over scheduler intervals, so a 4 ms loop can see a burst at full speed and then a stall. Before any figure from this mode is trusted, phase 3's first test spins a known load under a cap on this box and reports what the cap actually delivers. The real figures come from the board itself, in phase 6, and they replace the profile's assumed `speed.factor`.

### 3.4 Grade, per L3 and L4

| Part | Grade | Why |
|---|---|---|
| Engine world (X500 plus sensors) | whatever its modules claim, unchanged | the host adds no engine module |
| Budget-mode flight computer | `reference` | integer arithmetic on declared numbers, a golden: the same seed gives the same trace hash and the same overrun count |
| Measured-mode flight computer | `best-effort` | no golden, no band; it varies by design. It can become `banded` (L4) only with a measured band against budget mode and a record of how it was measured |
| A link and the software behind it | `best-effort` until shown repeatable | |
| The data in a profile | the library's five grades, per group | a different axis: an `assumed` speed factor does not lower the module's grade, but the report prints it |

### 3.5 A run's grade

`open(..., min_grade)` refuses a run that cannot meet the minimum (L3, L6): the run's grade is the weakest of the world's, the flight computer's mode, and the link's. A gate that needs `reference` refuses a measured-mode or live-autopilot run instead of silently downgrading it; the run report prints all three and the data grades.

## 4. The run record: Spade's side

One folder per run, written by `close()`. The Spade side is these files; the autopilot's log, the software's own log and the package hash arrive from their owners as paths and hashes the host copies into the manifest, opaque to Spade.

| File | Holds | Repeatable |
|---|---|---|
| `run.yaml` | run id, mode, Spade build id and commit, the engine's configuration hash and report, the world file hash, the model hash, every seed (world seeds and each reseed), `dt_ns`, `substeps`, the sensor periods, the profile and costs hashes, the link kind and version, the software's identity (an opaque tag), the three grades, and the **box and tree** for a measured run | yes, in budget mode |
| `trace.bin` | per tick: tick, truth (position, velocity, orientation, body rate), the applied rotor command, each new sensor sample; a rolling hash, and the final `trace_hash` | yes, given the commands and the seed (L1) |
| `commands.bin` | the command stream as applied: (tick, omega per rotor) | it is the input of a replay |
| `meters.yaml` | overruns, late and skipped samples, latency statistics per stage (min, mean, p99, max, ns), the memory peak (measured mode) | budget mode: exact; measured: as measured |
| `profile.board.yaml`, `costs.yaml` | copies, with hashes | yes |
| `manifest.yaml` | a SHA-256 for every file here and for each file the other owners supplied | yes |

- **Replay.** `fc_host --replay <run>` loads `commands.bin` and steps the same world with the same seed and no autopilot, and must reproduce `trace_hash` exactly. That is the guarantee Spade can make for any run, live or measured, and it is the first test of phase 1.
- **A live re-run** (same seed, the real autopilot) gives the same trace only if the autopilot is deterministic in lockstep. That is not assumed: the repeat test compares the two runs and lists every difference, as the map asks.
- **The signature.** Spade writes `manifest.yaml` as the payload to sign; who holds the key and signs the one run report is not Spade's to decide (question 3).
- **Cost.** `trace.bin` at 250 Hz with the X500's sensors is under a kilobyte per tick, so a 60 s run is a few megabytes; sweeps keep `commands.bin` and the hashes and regenerate the trace on demand.

### 4.1 As built (phase 1): `trace.bin` v1, `commands.bin` v1, the rolling hash

The source of truth is the comment in `tools/fc_host/lockstep.hpp` and the test `tests/test_fc_host_trace.cpp`, which reads the bytes with its own reader. Little-endian, IEEE `f32`, no padding; the world frame is Spade's own (+y up, right-handed). Agreed with Rendering; any change is told to Rendering first.

- **Header, 192 bytes.** 0 `"SPTR"`; 4 `u32` version 1; 8 `u32` header size; 12 `u32` flags 0; 16 `u64` `dt_ns`; 24 `u32` substeps; 28 `u32` rotor count `n`; 32 `u64` tick count; 40 `u64` first tick; 48 `u32` tick record size (76 + 12 n); 52 `u32` sample header size (16); 56 `u64` tick section offset; 64 `u64` sample section offset; 72 `u64` sample count; 80 four `u32` payload bytes of an IMU, GNSS, baro and mag sample; 96 `char[64]` `trace_hash` in lower-case hex; 160 `u64` `boot_steps`; 168 `u64` `boot_end_time_usec`; 176 `u64` boot seed (these three are 0 when no boot was noted); 184..192 zero.
- **Tick record.** `u64` tick; `u64` `time_ns` = (tick + 1) x `dt_ns`; `f32[3]` position; `f32[3]` velocity; `f32[4]` orientation (w, x, y, z); `f32[3]` body rate; `f32[n]` applied rotor command; `u32` first sample, `u32` sample count; `f32[n]` shaft speed; `f32[n]` blade azimuth in [0, 2 pi) (`physics/blade_azimuth.hpp`'s rule with h = `dt`, held on the host outside the registered state). The record is the state at the END of the tick.
- **Sample section.** One record per sample, `{u32 kind (1 IMU, 2 GNSS, 4 baro, 5 mag), u32 binding, u32 index, u32 0}` then the engine's sample struct. The host polls every bound sensor after every tick itself, so each sample is in the trace once whenever the caller takes them (`take_sensors()` returns what was polled; a late take loses nothing).
- **Trailer.** The last 64 bytes are the lower-case hex SHA-256 of every byte before them.
- **`trace_hash`.** h0 = SHA-256 of `spade.trace.v1`; h_k = SHA-256 of (h_(k-1), tick record k, that tick's sample records), as text bytes; the last h. The header and `run.yaml` carry it. It does not cover the header, so a boot of 3 steps and one of 300 give the same hash.
- **`commands.bin` v1.** `"SPCM"`, `u32` version 1, `u32` n, `u32` 0, `u64` count, then count records of `u64` tick and `f32[n]`: the command the rotors were given before that tick's step, after any latency. `replay_commands` applies them at those ticks with no queue and no autopilot and reproduces `trace_hash` and the bytes.
- **The boot phase.** While a firmware boots the world is held: `boot_readings(step)` reads the vehicle at its spawn state and steps nothing, with noise from a stream of its own, a pure function of (boot seed, step). `note_boot()` records how long the boot was. The sigmas and seed go in `run.yaml`.
- **The run folder.** `tools/fc_host/run_record.hpp` writes `run.yaml`, `trace.bin`, `commands.bin`, `meters.yaml`, `profile.board.yaml` and an unsigned `manifest.yaml` (the consumer signs), held to `tests/fc_run_folder_check.hpp`. Phase 1 writes measured runs; budget mode is phase 2.

## 6. Open questions, and what I would argue against

**Facts from the web, unverified.** PX4's simulator MAVLink API (TCP 4560): HIL_SENSOR in, HIL_ACTUATOR_CONTROLS out, lockstep. The docs of some versions say the simulator listens and PX4 connects; others say the opposite, so Interface checks the pinned release. PX4's SIH does not use this API, and PX4's Gazebo path uses its own bridge, so neither is a route for us. ArduPilot's JSON interface (UDP 9002): from ArduPilot, a magic number, `frame_rate`, `frame_count` and 16 PWM values; from the simulator, the timestamp, IMU, position, velocity and attitude. I did not confirm its lockstep rule, and I believe (from memory, to verify in phase 5) that ArduPilot's SITL synthesizes its own GPS, barometer and magnetometer from the state it is sent, so Spade's baro and mag, and sensor-fault injection through them, would not reach ArduPilot the way they reach PX4.

**What I would argue against.**

1. **The barometer and magnetometer are a phase 1 item.** To my knowledge PX4's preflight checks refuse to arm without a barometer and a compass. Phase 1 flies the X500 with PX4, so both are needed before the link tests, not after, in phase 4. Core's plumbing is small (2 to 3 days, the camera 3.1 pattern); the models are Physics'. Verify against the pinned release's checks.
2. **Budget first, measured later.** Budget mode is deterministic and carries the gates; measured mode is the more expensive half (effort 4), depends on the REALTIME runtime, and its figures need the phase 6 board to mean much. Build budget mode and phase 2 first; start measured mode only when phase 2 has passed. Call it "constrained", not "emulated".
3. **Loop rates only is right, with the output latency added.** Without a declared sensor-to-output delay for the flight controller the loop is optimistic by a few milliseconds that nobody can see. The latency is declared and graded `assumed`; phase 6 replaces it.
4. **PX4 first: agreed.** The X500 is its reference airframe, and the sensor path (HIL_SENSOR) takes Spade's sensors, which is the fidelity the owner asked for; ArduPilot's path may take less of them (above).
5. **Skipping QEMU: agreed.** It runs the real instruction set but not the board's timing, and it is slow.
6. **A phase 1 pass bar to refine.** "The same seed twice gives an identical Spade trace" holds under a live autopilot only if the autopilot is deterministic. State two bars: replay of the recorded commands gives the identical hash (always); the live repeat lists its differences.

**Open questions.**

1. A software component whose cost depends on its input (a planner): a constant per call (p99 or worst case) in v1; a per-mode table later, if a package needs it.
2. Does the Job Object's CPU cap behave on this box (hybrid cores or SMT)? Measured first in phase 3 before any use.
3. Who signs the run report, and with what key.
4. A host checkpoint beside the engine snapshot: if a run is restored, the host's queue and counters must be restored with it. The host writes its own file; the engine's snapshot does not carry it (L7).
5. The clock across a reset (section 2.3): a monotonic offset in the host, or a restart of the autopilot. Interface and Core decide with the first link test.
6. Is "this PC" a part? Proposed: no; a standalone `host`-kind profile with no part, and `compute: {board: ...}` on a part only for a physical board.
7. The MAVLink headers (MIT) and PX4's source and toolchain, and later ArduPilot's, are downloads: the list goes to the owner before any fetch, from Interface and Vantage, not from `fc_host`, which needs none beyond what the repo already has.
