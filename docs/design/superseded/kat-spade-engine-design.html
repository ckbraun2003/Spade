§0

What this document is

The foundation charter (seventh spec) pinned Spade's identity and eight pillars, then deliberately deferred the engineering to this session. This document is that engineering: every §8-owed item is answered here, grounded in a line-level dive of the v1 codebase (§13 carries the keep/kill verdicts). Spade is designed as a general extreme-fidelity, high-throughput physics + rendering engine — Kat is its first consumer, not its shape. The long-term arc is modeling and rendering the aerodynamics of motorized vehicles; the quadrotor is the first vehicle model class, not the point.

Binding context

Charter pillars P1–P8 govern (GPU-authoritative + CPU reference twin · three-grade determinism · Vulkan · fixed-step/seeded · fat-Spade/thin-dronesim · offscreen render · effects→aero promotion rule · snapshot first-class). The editor technical spec's TA1 (C5 presentation semantics) and TA5 (sensor-poll convention) bind the frame and sensor surfaces (§9, §7). Where this document details a mechanism the charter only named, this document governs.

§3

The step model

v1 has no concept of a step — the substep loop lives in the sandbox. v2 makes the step the engine's central object: deterministic, declared, inspectable.

  • Fixed dt, immutable at creation (C5). A Simulation owns a WorldSet and steps it: step(n_steps). Substep count per world config; effective substep dt = dt / substeps.
  • The substep pipeline is a fixed, declared pass sequence:
// per substep, in this order, always:
MediumUpdate      // Dryden gust states advance (seeded, per world)
ForceElements     // rotors -> drag -> lift surfaces (each element type = one batched pass)
Gravity
CollisionStatic   // dynamic proxies vs world SDF: distance + gradient -> contact impulses
CollisionDynamic  // sorted-grid pair path (exact cell compare — v1 hash-collision bug fixed)
Integrate         // symplectic Euler + quaternion exp-map; captures specific force for sensors
SensorSynthesis   // only on sensor-rate boundaries; writes sensor output rings
Publish           // tick counter++, snapshot ring hook, frame-state copy point

[Two corrections to this shorthand ratified in Addendum A — A9: the tick counter increments once per step, not in the per-substep Publish pass (schedule.hpp:328-338); and the Gravity pass is deliberately inert — gravity is applied inside Integrate for exact specific-force capture (schedule.hpp:265-282). The landed schedule is normative; see §15 A9.]

  • Every pass is one interface, two implementations — execute_cpu(WorldSpan) and record_gpu(CommandRecorder&) — same math, same operation order, fp32 both (P1/P2). The schedule object is data; passes cannot reorder themselves.
  • Determinism: no wall-clock anywhere below Simulation; every stochastic element (Dryden, sensor noise, spawn randomization) draws from per-world, per-system splitmix64 streams domain-separated from the world seed (the errata-R4 discipline, engine-generic). Structural changes (spawn/despawn/model load) are queued and applied only at step boundaries.
§4

State, many-worlds, snapshot

State layout

  • Authoritative state is SoA arenas partitioned by world: bodies/elements/sensors occupy world-contiguous slot ranges inside global arrays. Per-world parameters (gravity, medium, capacities, seed) live in an indexed param buffer. A slot→world map buffer lets one dispatch cover all worlds.
  • Fixed capacity per world at creation (bodies, elements, sensors, contacts). Spawn/despawn (C5 calls) allocate/free slots deterministically in call order within capacity — no reallocation mid-run, ever. v1's "Load-then-never-again" becomes an explicit, honest contract instead of a silent overrun.
  • The ECS carries identity, not physics: generational handles (index+generation, reuse-safe — v1 had no lifecycle at all), components reference state slots. Pool iteration order no longer feeds GPU buffer order; slot assignment does. Component type IDs are compile-time registered monotonic (v1's dead GetUniqueComponentID pattern, resurrected), never typeid().hash_code().
  • Static world geometry (the SDF program, §5) is immutable per world in its own buffer; rebuilding it is a structural change.

Many-worlds (D8)

  • The collision grid hashes (world_id, cell); sorted domains are global; range checks make cross-world interaction structurally impossible. One dispatch steps N worlds; N=1 is the degenerate case with no overhead.
  • The CPU twin iterates worlds serially with identical per-world math — parity comparisons are per-world, so a divergence names its world.
  • A WorldSet template ("N worlds from this world file, capacities X") is the training-fleet constructor; heterogeneous sets are allowed but uniform sets get the tightest layouts.

Snapshot (P8) and readback

  • The state registry records every authoritative array (name, element type, per-world extents). Snapshot = registry walk → versioned blob: header (schema hash, tick, world set shape) + arena copies + RNG stream states. CPU path = memcpy. Restore = reverse + structural-queue flush. Blobs save/load to file — the determinism-replay corpus is snapshot pairs + input scripts.
  • GPU path: on-demand snapshot = one arena→staging copy at a tick boundary (single vkCmdCopyBuffer, fence, map). The editor's continuous rewind ring = async double-buffered staging copies every K ticks, never blocking the physics queue.
  • Sensors solve the per-tick readback problem: sensor outputs are tiny; they live in a dedicated output buffer read back per tick (double-buffered). Full-state readback happens only on demand. Nothing else crosses the bus per tick.
§5

Physics content

Rigid bodies (D1, D2)

  • State per body: position, velocity, orientation quaternion, angular velocity (body frame), mass, inverse inertia tensor (body frame), accumulators (force, torque), flags. Layout defined once in shaders/shared/ (§8).
  • Integration: semi-implicit Euler — velocities first from accumulated wrench, then pose; orientation advanced by q ⊗ exp(½ ω dt) (exact for constant ω over the substep); Euler's rigid-body term (ω × Iω) included; quaternion renormalized per substep (deterministic op order).
  • Specific force (acceleration minus gravity, body frame) is captured inside Integrate for the IMU pass — computed once, not reconstructed.

Collision (D3)

  • Static world = an analytic SDF program: primitives (plane, box, sphere, cylinder, capsule, torus, heightfield) + transforms + CSG ops (union, intersect, subtract, smooth variants) compiled by the WorldBuilder into a flattened postfix node program. Both backends evaluate the identical program (§8 single-sourcing). Contact = φ(p) < r ⇒ depth, normal = ∇φ (analytic where closed-form, central differences otherwise — pinned stencil for parity).
  • Race gates are box/torus compositions — exact geometry, zero mesh error. Contact response: impulse-based with restitution + Coulomb friction (v1's model, kept), positional correction clamped.
  • Dynamic–dynamic: the v1 sorted-grid pipeline ports (atomics-free design kept — it is the engine's best idea), with fixes: exact cell-ID compare (hash-bucket neighbors bug), bounds-checked bitonic tail, hash size configurable per world set (not a 4×-duplicated constant).
  • Dynamic proxies v2: sphere and capsule. Convex hulls and triangle-mesh statics are the stated later rungs.

Medium & aero (D5, D6)

  • Medium interface: sample(world, position) → {density, wind_velocity}. v2 implementation: per-world density + constant wind + Dryden turbulence (standard MIL-spec form, per-world seeded filter states advanced in MediumUpdate). P7's flow fields implement the same interface later — aero code never knows which medium it reads.
  • Aero force elements read Medium at their body-frame station: RotorElement (§6), DragBody (quadratic + componentwise, matching what current KAT configs express), LiftSurface (flat-plate + polar tables — the fixed-wing seat, post-v2).
§6

Vehicles — the model-type layer

The pattern

A ModelType is an engine asset class one tier above shapes and meshes: rigid-body template (mass, inertia, proxies) + force-element set + sensor mounts + visual mesh references + a parameter schema. Instances spawn from a ModelType into slot allocations. The Quadrotor is the first ModelType; cars and fixed-wing arrive as new element types + model classes — nothing vehicle-specific exists below vehicles/.

RotorElement (D5)

// per rotor, SoA, batched across all worlds:
params:  body slot · local pose · spin dir · time-constant τ (RPM lag)
         thrust curve T(ω) · torque curve Q(ω)   // polynomial or table
state:   ω (RPM)                                  // first-order lag toward command
step:    ω += (ω_cmd − ω)·dt/τ
         v_axial = axis · (v_body + ω_b × r − medium.wind)
         T = T(ω) · f_inflow(v_axial)             // momentum-theory correction:
                                                  // climb/descent/hover thrust variation
         T *= f_ground(φ_world(p_rotor))          // ground effect from the WORLD SDF —
                                                  // the collision field IS the proximity query
         apply wrench {T·axis, Q(ω)·spin + T·axis × r} at body
  • Quadrotor API: a parameter struct (rotor poses or arm-geometry shorthand, mass/inertia, per-rotor params, drag body, sensor mounts, visual mesh ref) + factory → ModelType. Convenience accessors for command vectors (per-rotor ω_cmd or normalized u). This is the class Kat's dronesim maps drone descriptions onto.
  • Gyroscopic rotor terms and BEMT are per-rotor opt-ins on the roadmap; the param schema reserves their fields now so upgrading a model never changes layout.
  • Aero roadmap (charter P7): BEMT per rotor → effects-layer flow fields (rotor wake, downwash) feeding Medium.sample as local inflow. Promotion to authoritative requires the CPU twin mirroring — restated here because it guards this exact path.
§7

Sensors

  • Sensor tables (SoA, batched): kind · body slot · mount pose · rate divider · seeded noise params · output ring reference. Synthesis runs inside the step (SensorSynthesis pass) only on that sensor's rate boundary.
  • IMU (v2): gyro = body ω at mount (+ lever-arm terms), accel = specific force at mount transformed by mount pose; noise = white + bias random walk per axis, per-sensor seeded streams. Output = timestamped samples into the sensor's ring.
  • Output rings: monotonically indexed, tick-stamped samples in the per-tick readback buffer. The host polls rings (C5 kathost_sensor_poll); ring depth ≥ the host's worst poll interval; the count/latest-index convention follows the editor tech spec's TA5. Spade exposes samples + indices; stamping policy above the seam belongs to dronesim (P5).
  • Camera sensors — seat reserved, phase S7+: a camera sensor is a render-to-texture at sensor rate on the render queue, output = image + tick. Explicitly distinct from presentation frames (TA1's domain, §9): sensor frames are simulation outputs and must exist headless; presentation frames are for humans. Keeping the two frame kinds separate is what keeps render-cadence invariance (TA1) and headless sensor fidelity simultaneously true. [Superseded for sensors by Addendum A — A1: camera-sensor synthesis executes inside stepping, in the reserved SensorSynthesis pass; presentation frames stay on the render path. See §15 A1.]
§8

Worlds & the file format

  • WorldBuilder (fluent API): add SDF nodes (primitive, transform, material, CSG op), spawn points (named poses), environment (gravity vector, medium params, default seed), capacities. build() validates (capacity sanity, SDF program depth, name uniqueness) → immutable WorldDesc.
  • World file: versioned YAML serializing exactly the builder's product — world_version, environment, sdf scene tree, spawns, capacities, visual attachments (mesh refs, render-only). Load = parse → same validation → WorldDesc. C5's world_ref = a file path or an in-memory WorldDesc handle.
  • Golden-world test corpus = world files + input scripts + expected snapshots: data, not code.
  • glTF import (visual meshes attached to bodies/statics) is a later, render-only add-on; physics never reads imported meshes until triangle-mesh colliders land (D3's later rung).
§9

Compute backends, Slang, parity — and frames

Single-source layouts (D9)

  • All shared state/param structs and the binding registry are authored once as Slang modules under engine/shaders/shared/. A build step (slangc reflection) generates the C++ headers with static_asserted offsets/sizes. v1's two worst layout hazards — 9-file struct duplication and the GLM quaternion-order coincidence — become build errors instead of silent corruption.
  • Kernels are Slang, compiled to SPIR-V at build; pipeline layouts and descriptor bindings come from the generated registry. No string-name uniform lookups; push constants + param buffers only.

Vulkan backend structure

  • compute/vulkan/ owns instance/device/queues: one compute queue for physics, one transfer queue for readback/snapshot, (S7) one graphics queue for render. Headless by construction — no surface required for physics or camera sensors.
  • Command recording per step: passes record into one command buffer per step batch; barriers between passes are explicit and minimal (v1's barrier-after-every-dispatch becomes stage-scoped barriers; the bitonic sort records its full dispatch chain once per shape and reuses it).
  • Timestamps queries per pass feed the bench harness — the budget numbers stop being guesses.

Parity (P1/P2 mechanics)

  • Golden scenario corpus (world file + inputs + N steps) runs on both backends; comparison per state array with per-quantity tolerance classes (positions, velocities, quaternions, RPM). CPU↔CPU replay must be bit-identical per platform; GPU↔GPU bit-identical per device+driver; CPU↔GPU within bands. Tolerances are measured then pinned with margin — the consolidation's golden-atol lesson (calibrate cross-platform before pinning) is standing policy.

Presentation frames (TA1 compliance)

  • The render module (S7) exposes a FramePool: explicit render(world, camera, target), ≥2 outstanding frames, non-blocking acquire, every frame tagged with its simulation tick. Rendering reads a tick-boundary state copy on its own queue — render cadence cannot perturb stepping, satisfying TA1's render-cadence invariance and the C5 headless/rendered equivalence test by construction. At M1b, Spade privately owns the graphics context exactly as the editor tech spec assumes. [B10's deferral rule recorded in Addendum A — A2; B11's discharge note in A5. See §15.]
§10

Rendering (S7) — designed now, built later

  • Offscreen-first (P6): instanced mesh pipeline (v1's flatten + instanceStartIndex scheme kept), color/velocity/wireframe debug modes carried over.
  • The SDF world renders by raymarching the physics field — the debug view draws the exact geometry collision sees; visual world and physics world cannot disagree. Materials attach to SDF nodes.
  • Dear ImGui becomes the engine debug HUD (pass timings, world/slot inspector, medium probes) — the dependency v1 linked and never used finally earns its place.
  • The v1 GL sandbox retires only when the Vulkan sandbox (window + swapchain over the same FramePool) reaches feature parity: the strangler's endpoint.
§11

API surface & conventions

  • namespace spade; C++23. Public API returns std::expected<T, spade::Error>; no exceptions cross the boundary (v1's uncatchable private exception classes are the counterexample). Error carries code + context string; an error-sink callback surfaces async/GPU-side faults. Debug builds run Vulkan validation layers; device-lost and OOM paths are explicit.
  • Typed RAII handles everywhere (WorldHandle, ModelTypeHandle, BodyRef, FrameHandle…) — never bare integer aliases (v1's GLuint soup). No globals; no process-wide teardown side effects (v1's glfwTerminate-in-destructor); N Simulations in one process is a supported, tested configuration (charter instance-isolation gap closed by construction).
  • Threading contract: a Simulation is externally synchronized (one caller thread); internal GPU queues are the engine's business; the render module may be driven from a second thread against the FramePool only.
  • Rule-of-five discipline on every resource-owning type (v1's MeshComponent double-delete landmine is the counterexample); moves explicit, copies deleted unless value-semantic.

A1 · B1 camera placement — ratified as the schedule already leans

Camera-sensor synthesis executes inside stepping, in the schedule's reserved SensorSynthesis pass (schedule.hpp:310-324), exactly as B1 requires; §7's camera-on-the-render-queue reading is superseded for sensors. Presentation frames stay on the render path (TA1 FramePool, S7) — "camera sensors ≠ presentation frames" stands. When the rendered camera lands (S7), its work is dispatched from within the SensorSynthesis pass (record_gpu), not the presentation queue; adding it adds no pass (the slot exists) but does change the snapshot schema hash + golden digests when camera state registers — declared-schedule discipline, re-record per §12.

A2 · B10 frame-pool deferral — recorded for S7

The FramePool must satisfy B10: frames handed to the host remain valid across all host calls; pool slots are deferred, not recycled, while frames are outstanding; ≥2 outstanding supported. No landed code affected.

A3 · B12 reset — restore + reseed surface

User-ruled 2026-08-10

kathost_reset = restore of an initial snapshot taken after roster assembly (roster preserved per B12), plus one new engine surface (e.g. Simulation::reseed(seed)) that re-derives all RNG streams from a fresh seed post-restore per R4's domain-separated derivation — necessary because WorldParams::seed is registered state inside the blob and restore alone reinstates the old seed.

The landed restore() semantics are ratified as correct (structural queue discarded; config/dt not in the blob). dronesim (the C5 implementer) must capture the post-roster snapshot at session start. Conformance: "reset preserves roster" round-trip + "reseed re-derives streams deterministically" cases added to §12's suite list.

A4 · B13 poll cursor — discharged by T19's landed shape, ratified

Every per-sensor cursor-bearing state (ring write cursor last_index, bias states, RNG stream, phase counter) is registered state inside the world snapshot blob (landed, ec5289f); poll(sensor, since_index) is caller-carried, stateless engine-side. The host-side consumed-sample cursor — B13's "poll cursor" at the C5 level — therefore belongs to the world-snapshot layer owned by dronesim (R9's world/runtime/session split): the host snapshots its own since_index values alongside the engine blob. The register's "B13 lands inside S2's snapshot round-trip suites" expectation is re-scoped: the engine-side obligation landed with T19's tests (ring wrap, poll-since, snapshot resume); the host-side cursor case lands in the C5 conformance suite (M1b).

A5 · B11 discharge note

The render-thread question formally moved to this session is answered: v1 renders on the sim thread (B11's sim-thread-render v1 posture; the strangler viewer conforms); the S7 target remains §11's second render thread consuming only the FramePool — satisfying B11's threading clause. Degradation order = renders drop first (B11): presentation frame production may be shed under load; sensor synthesis inside stepping is never shed.

A6 · Camera cost model (owed by batch 2 §1) — model now, numbers at S7 entry

Rendered camera ≈ n_drones × (W×H) × k_raymarch(SDF node count) per sample at 25 Hz; the synthetic-feature path (A8) ≈ n_drones × n_gates_in_frustum × k_sdf_query — negligible against R10's envelope. S7's entry gate benches the rendered model against the 3-drone × 25 Hz envelope; a miss triggers design review per §12's bench-miss rule (resolution options — resolution/rate reduction, GPU-only camera — recorded then).

A7 · The opaque backend config block (owed by config §18)
