Spade & Sim Stack — Foundation Charter

The seventh Kat spec: what Spade is, the architecture pillars it commits to, how the repo moved into the monorepo, and where it sits on the milestone ladder. A charter, not an engine design — the technicals are deliberately deferred.

approved v1.0 · 2026-08-06 amends: errata R1 · R11 · C5 determinism repo state: spade/ subtree-merged at 1c8a133
§0

What this document is

The errata (sixth spec, approved 2026-08-06) created a hole on purpose: C5 — the sim-host contract — got a surface and a conformance suite, but the engine beneath it had no spec, no repo presence, and a survey showing that its current state and its obligations describe different software. This charter closes the setup half of that hole: identity, pillars, repo integration, milestone placement, and an honest gap register.

It deliberately does not design the engine. Buffer layouts, the many-worlds batching model, rate envelopes, API surfaces, Vulkan module structure — all of that belongs to a dedicated engine design session held now that the repo is in the tree (§8 lists what that session owes). Two implementers reading this document should agree on what Spade is and what it must become, and should refuse to start building until the engine session pins how.

Precedence

Where this document touches the errata, this document governs (§4 lists the three amendments). Everywhere else, the approved errata governs over the five v1.0 specs, per its own §0.

§1

The sim stack

editor viewport · kat-train rollouts · kat CLI
        │  C5 — the sim-host contract (errata R1: surface, conformance, semver)
        ▼
dronesim            // implements C5. Thin adapter: contract surface, drone
        │           // assembly (drone description → engine bodies/aero/actuators),
        │           // Kat-side timing & sample stamping. No physics of its own.
        ▼
spade/              // the engine. Owns rigid bodies, collision, aerodynamics,
                    // propulsion/actuator force models, sensor-simulation
                    // primitives, rendering, worlds. No Kat types in its API.
Boundary ruling

Fat Spade, thin dronesim. Everything that can live in the engine does — including aerodynamics, propulsion force models, and sensor-simulation primitives (IMU synthesis, camera render-to-sensor). dronesim contributes no physics: it is the C5 surface, the mapping from a drone description onto engine constructs, and Kat-side stamping. This maximizes what Spade grows into while keeping the contract seam exactly where the errata put it.

Consequence worth stating: because dronesim is thin, C5 conformance effectively tests Spade through a narrow adapter — engine regressions surface as contract failures, which is the intended coupling.

§2

Identity

Spade is a high-fidelity, low-latency, high-throughput physics and rendering engine: complex rigid-body collision, aerodynamics, extreme-accuracy step rates — written primarily in GPU compute, operable CPU-only, optimized for GPU. It is Kat's engine, cleanly bounded: it exists to serve Kat's sim stack, keeps a no-Kat-types API so extraction stays possible, and spends no energy on standalone packaging or independent releases.

v2 is a modification/addition/refine stage — not a rewrite

The 2026-08-06 survey confirmed the foundations fit: the data-oriented ECS, the compute-pass structure, the std430 POD state layout (memcpy-able by design), and the atomics-free one-invocation-per-index shader discipline — the exact property that makes same-device GPU determinism achievable — all carry forward. What changes is plumbing and discipline (§7), not architecture.

§3

Architecture pillars

Eight commitments, decided 2026-08-06. Each is one sentence here; the engine session expands them into designs.

#PillarCommitment
P1CPU reference twinEvery authoritative physics pass exists twice — GPU compute (primary, performance) and CPU (reference) — kept in enforced tolerance-banded parity by the fixtures pattern this project already lives by. The twin is not a degraded fallback: it is the determinism reference and a full implementation.
P2Three-grade determinismCPU path: bit-identical per platform — the conformance grade; CI enforces it and golden traces are recorded from the CPU path only. GPU path: bit-identical per device+driver — same-machine replay and editor step-back work. CPU↔GPU: tolerance-banded parity. (Amends C5 — §4·A3.)
P3VulkanThe GPU path moves to Vulkan: true headless compute, offscreen render, explicit sync, a Linux/cloud-training route, and GLSL→SPIR-V carries the existing shader logic. GLFW/GL survive only as long as the port takes.
P4Fixed-step, seededFixed-step only; no wall-clock read anywhere in the step path; every RNG is seeded and domain-separated in the R4 style. dt is immutable after creation, per C5.
P5Thin adapter aboveThe §1 boundary: Spade owns the physics and sensor primitives; dronesim owns the contract surface and assembly. No Kat types below the C5 seam.
P6Offscreen render boundarySpade renders the world to an offscreen image; the editor imports it and composites UI on top. Headless = simply don't render. Stepping never depends on render state (C5 conformance test).
P7Effects layer → aero pathThe v1 SPH/grid/particle machinery survives as the non-authoritative effects/medium layer, with a stated roadmap toward air-flow simulation (downwash, prop wash, wind fields). Promotion rule: nothing becomes authoritative until the CPU twin can mirror it (P1 applies to every authoritative pass, no exceptions).
P8Snapshot as first-classWorld snapshot/save/restore is a core engine feature (C5 §world-snapshot, errata R9), sized and designed for the editor's session ring and training determinism — not an afterthought serializer.
§4

Amendments to the approved errata

Namespace note (batch 2 §0, 2026-08-08): the A1–A3 identifiers below are retroactively SA1–SA3 — the editor technical spec's amendment series is TA1–TA6, and bare "An" citations are retired. Text below is unchanged; cite these as SA1–SA3.

Three decisions made in this spec's session supersede specific errata statements, per the docs-spec supersession rule.

IDErrata saidNow reads
A1R11·M1b: "C5 + dronesim: interim C++ physics behind the sim host."Spade is the M1b backend. No interim C++ physics backend is built; M1b's bar is Spade's M1B-tagged gap set (§6). The current KAT sim code is still mined for reference and test oracles, but never becomes a C5 implementation.
A2R1: "The two conformant backends at M1b are the interim C++ physics and dronesim-on-Spade."The cross-backend parity pair is Spade's CPU twin ↔ Spade's GPU path — two implementations of the same passes inside one engine, compared through the same C5 seam. golden-parity's widened definition ("any two implementations of a Kat contract") already covers this; the twin is the second implementation.
A3R1: C5 conformance = "bit-identical body state and sensor output, per platform."Three grades (P2): CPU per-platform bit-identity is the conformance claim and CI's gate; GPU is bit-identical per device+driver; CPU↔GPU parity is tolerance-banded. Golden traces come from the CPU path only.
A1's accepted risk — stated, not hidden

M1's critical path now runs through engine work. What buys that back: M1a (runtime skeleton) has no world dependency and proceeds in parallel; the CPU twin lands first (§6) and is dramatically less work than the Vulkan port; and building one backend instead of two deletes an entire throwaway implementation.

§6

Milestone placement

Ruling

Spade is the M1b backend (§4·A1). M1b's minimum bar is the §7 rows tagged M1B: fixed-step, headless, seeded determinism, snapshot/restore, and rigid-body dynamics + collision + force models sufficient to fly a racing track through the C5 seam.

Sequencing inside M1b

  • CPU twin first. The CPU reference path alone satisfies M1b's proof — a package flies a track headless and passes determinism replay — with no Vulkan work on the critical path. It is also how the twin earns its P1 role from day one: the reference exists before the thing it references.
  • Vulkan GPU path second, on its own clock, joining as the parity partner (§4·A2). The parity harness stands up the moment both paths exist, per the existing fixtures pattern.
  • M1a (runtime skeleton) is untouched by any of this; M1c/M1d follow the errata as approved.

§8

Owed by the engine design session

  • Many-worlds model — batched worlds in one dispatch vs. process instances vs. both; where the world index lives in the data layout. (The GPU-authoritative choice pays off or doesn't largely here.)
  • Buffer & state layout — the authoritative state set, CPU↔GPU mirroring scheme, readback design, snapshot format.
  • Rate envelope — actual numbers: physics substep targets, real-time viewport scale, headless training throughput targets.
  • Sensor primitive set — which sensors are engine features and their synthesis models.
  • Vulkan module structure — device/queue/context ownership, offscreen image handoff to Qt (P6 mechanism), shader toolchain.
  • Kat build wiring — how kat targets consume the Spade subproject; toolchain alignment with the interface build.
  • SPH → aero promotion criteria — what the effects layer must demonstrate before P7 promotion.
  • Dead-code cleanup — the §9 list, adjudicated item by item (delete vs. finish).
  • Linux/cloud timing — when platform unlock enters the schedule.
