Design specification · twenty-fourth spec · draft

Spade — The Library, Its Object Model, and the Sandbox

Spade is a general physics and rendering engine, and this spec says so normatively. It restores the object/component model the v2 rewrite dropped, defines what a behavior can be in a fixed-step bit-deterministic engine, completes the v1→v2 system transfer that was left unfinished, and builds spade_sandbox — an engine editor that makes physics and rendering observable instead of inferred. The frozen v1 GL engine is then quarantined, but only after every system it holds exists in v2 and every scene it demonstrates has a working successor.

§0

What this document is

This spec drops the Kat — title prefix every other document in the corpus carries. That is deliberate and it is the thesis: Spade is not a Kat subsystem that happens to live in spade/. It is a general-purpose physics and rendering engine of which Kat is one consumer. The filename keeps the corpus kat- convention so the register and the artifact tooling stay uniform; the title does not.

Three things prompted it. First, the engine is already generic where it counts and nothing says so normatively — vehicles/quadrotor.hpp's own header states that "there is no Quadrotor class, no quadrotor-shaped code path in the Simulation, and no quadrotor branch in any pass. If this file were deleted, the engine would still fly quadrotors." That discipline is being held by comment and habit rather than by specification. Second, the object/component model the engine design ratified in §4 does not exist in code: the identity half was built, the composition half was not, and the model it points back at is sitting in the v1 tree scheduled for deletion. Third, there is no way to look at the engine. The only interactive tool renders v2 physics through the frozen v1 OpenGL engine across a bridge translation unit that needs <windows.h> included first to dodge a macro collision, and carries its own relaxed warning policy because v1 cannot survive /W4 /WX.

Session rulings absorbed (user, 2026-08-30)

① Spade is a blanket physics/render engine — objects, meshes, components, physics, behaviors — and the sandbox behaves accordingly. ② Isolation is hardened in place: Spade stays in the monorepo and gains a provable standalone identity, not a separate repository. ③ The sandbox is a viewer plus inspection plus exploration that saves its own scenes, and does not author canonical content. ④ The object model is designed in full and built minimally. ⑤ Behaviors are declared and deterministic, joining the pass schedule as data. ⑥ Both Spade and Kat keep the word "component", separated by context. ⑦ v1 is quarantined to spade/legacy/, not deleted, and completely cut off from any functionality or system. ⑧ The retired scenes need equivalent presets, not numerically exact ports — but every system v1 holds must first exist in v2. ⑨ The 21st spec's Task C4 is slotted after C3, so the render program merges on a clean base before this program starts.

§1

SL1 — Spade is a blanket engine

SL1 · the engine is domain-neutral, normatively

Spade's core — core, state, world, physics, render, sim, compute — carries no domain concept. It knows bodies, elements, contacts, meshes, materials, lights, sensors and worlds. It does not know drones, missions, gates, policies or packages.

Domain vocabulary lives in convenience layers above the core that construct general descriptions and add no code path of their own. vehicles/ and sensors/ are exactly this and stay where they are: make_quadrotor() constructs a ModelType from a dozen numbers, and deleting it would cost callers convenience, not capability.

The test of a proposed engine addition is whether a caller with no aerial-vehicle interest would still want it. A fluid solver passes. A gate-pass detector does not.

Where the boundary is enforced today

Two guards already hold the Kat side of this line and are unchanged by this spec. HS2 rule 1: nothing under spade/ may depend on Kat. HS2 rule 2: no Spade engine header may appear outside dronesim/spade/. Both are enforced by tools/tests/test_engine_agnosticism.py, which went red during the render program's Task C0 and caught a real violation — the guard is live, not decorative.

What has never been stated is the other direction, and SL1 states it: the engine may not grow a Kat-shaped concept even in a Kat-free form. A guard cannot catch that; only a specification can.

§2

SL2 — The library surface and its hardening

Spade is already a well-formed installable library, and this section is deliberately narrow because of it. Eleven modules, each a static library with a spade:: namespaced alias, install(TARGETS ... EXPORT spadeTargets), per-module header installation, and a generated spadeConfig.cmake. An out-of-tree find_package(spade CONFIG REQUIRED) consumer project is configured, built and run by CI on both Linux and Windows against a scratch install prefix — and it is load-bearing rather than ceremonial: it is what caught the yaml-cpp consumer-link gap that the in-tree tests structurally could not see, because a static archive only extracts the members it needs.

Severability is likewise already proven rather than aspirational. scripts/spade-prefix.ps1 has built Kat's Spade install with -DSPADE_BUILD_V1=OFF from the beginning: Kat has never linked v1.

SL2a · release identity

Spade gains its own release identity: spade/CHANGELOG.md, a stated versioning policy for project(Spade VERSION ...) (currently a bare 0.2.0 with no release notes behind it), and a spade/README.md quickstart that stands on its own — buildable, installable and consumable by a reader who has never heard of Kat. Today's README opens by defining Spade as "Kat's simulation engine"; that framing is corrected.

Not in scope: a package registry, binary distribution, or an ABI-stability promise. Those belong to seat S1 if they are ever wanted.

The repository situation, stated so it stops being ambiguous (user, 2026-08-30): Spade has its own upstream git repository, unrelated to Kat, which is where v1 lives. The copy under spade/ is subtree-merged into this monorepo — 185 tracked files, no submodule, not ignored — and is the development home: Spade is built and tested inside Kat for development convenience, and is freely editable here. Both facts hold at once. "Harden in place" therefore means hardening the development home, and is not a claim that no external Spade exists. It also makes SL14a's quarantine-rather-than-delete the obviously correct call: v1's history survives in two places, so nothing is at risk, and the local copy stays available as a reference.

SL2b · the sandbox may use only Spade's public installed surface

spade_sandbox may include only headers that install(DIRECTORY ...) actually installs, and may link only spade:: targets. It may not reach into engine internals by relative path, and it may not depend on anything the exported package does not carry.

Why this is the highest-value constraint in the spec: the sandbox is the library's largest consumer, so this makes it a continuous proof that the public API is sufficient. If the sandbox needs something the API does not expose, that is a finding about the library rather than a reason to widen an include path. Enforced by a guard over the sandbox's include graph, in the same shape as the existing agnosticism guard.

§3

SL3–SL5 — The object model

The engine design spec §4 already ratified this and the code only half-implements it:

Engine design §4, verbatim

"The ECS carries identity, not physics: generational handles (index+generation, reuse-safe — v1 had no lifecycle at all), components reference state slots. Pool iteration order no longer feeds GPU buffer order; slot assignment does. Component type IDs are compile-time registered monotonic (v1's dead GetUniqueComponentID pattern, resurrected), never typeid().hash_code()."

Built: the identity half — core/ids.hpp's generational Handle (index + generation, generation 0 reserved for "never issued") and sim/simulation.hpp's BodyRef, whose generation counter lives in a registered array (body_generation) so lifecycle survives the snapshot walk.

Not built: the composition half. There is no component type, no compile-time type-ID registry, and no attachment mechanism anywhere in spade/engine/. Bodies, force elements, sensors and render instances are parallel concepts addressed through separate APIs rather than parts of one thing.

SL3 · the object graph is composition and identity, never state — and therefore determinism-neutral

§4's clause "pool iteration order no longer feeds GPU buffer order; slot assignment does" is the load-bearing property, and this spec makes it explicit and permanent: the object graph never influences buffer layout, pass order, or any value the physics computes. Objects and components may be created, reordered, renamed and destroyed freely, because slot assignment — which already exists and is already deterministic — is what the GPU sees.

It follows that the object graph is not registered state. It is composition, reconstructed from the scene or world description; components hold handles into the existing SoA arenas and never own physics data. Consequences, all of which are the point: kSnapshotVersion does not change; the registry walk does not change; every existing CPU↔GPU parity band and determinism test remains valid unmodified; and a snapshot taken before this model existed still restores after it.

Cost if wrong: if a future component genuinely needs to own persistent state, it must be registered and the snapshot version bumped — a known, bounded, deliberate change rather than a silent one.

SL4 · the component model, specified in full

Object — a generational handle plus a stable name, owned by an ObjectGraph. An object has a transform and zero or more attached components. Objects may nest; nesting affects transform composition only and never pass order.

The container is named ObjectGraph, not Scene, deliberately: spade::render::RenderScene already exists and means something different (the renderer's per-frame view of a world). Two things called a scene, one namespace apart, is a prose trap even where C++ would disambiguate them.

Component — a typed part attached to exactly one object. A component holds configuration plus references to engine state slots; it does not hold simulation state. Component type IDs are compile-time registered and monotonic, never typeid().hash_code(), because the id is what a saved scene stores and a hash is neither stable across compilers nor meaningful across versions.

Lifecycle — attach and detach are structural changes and obey the engine's existing rule: queued, applied only at step boundaries, never mid-step. This inherits the discipline rather than inventing a second one.

Serialization — an object graph serializes by component type id plus configuration; slot references resolve at load. A saved scene therefore survives a change in slot assignment, which is exactly why the id is registered rather than positional.

SL5 · what this program actually builds

The model above is specified in full. Implementation is limited to the component types the sandbox exercises — ten of them: Transform · Body (references a body slot) · Mesh (references a render draw item) · Material · Collider (SDF or sphere proxy) · Sensor (references a sensor slot) · ForceElement (rotor or drag) · Camera · Behavior (§4) · Fluid (§5's SL8, arriving with that phase rather than P1).

This is not v1's set replayed. Of v1's eight, Transform, Mesh, Material, Camera and Fluid carry across by name; Motion folds into Body and Bounding into Collider, since v2 already owns both concepts in its state arenas; and Input does not become an engine component at all (SL9d). Body, Sensor, ForceElement and Behavior are new, because v2 has state layers v1 never had.

Everything else the full ECS eventually wants — queries, systems iterating by component signature, archetype storage — is designed against, not built. The reason for the split is that inventing the model twice is the expensive failure; building it incrementally against a settled design is not.

The content layer reached this vocabulary first: content/recipes/*.json already describes scenes as instances of prefabs with poses. SL4 gives the engine the same shape the recipes have been using, which is why the sandbox and the recipe format will map onto each other cleanly at §6.

§4

SL6 — Behaviors

"Behavior" is the one word in the framing with no precedent anywhere in the corpus, and the naive form of it is incompatible with guarantees the engine is built on. The pass schedule is data and "passes cannot reorder themselves"; there is "no wall-clock anywhere below Simulation"; every pass is one interface with two implementations, execute_cpu(WorldSpan) and record_gpu(CommandRecorder&), "same math, same operation order, fp32 both". A Unity-style MonoBehaviour — arbitrary user code, arbitrary order, per-frame — violates every one of those, and would not fail loudly. It would quietly destroy CPU↔GPU parity, which is the property the entire GPU program was built to establish.

SL6 · a behavior is a declared, ordered, fixed-step pass

A behavior declares, at registration: a stable name; which of two fixed behavior slots it runs in; the components it reads and writes; and an execute_cpu implementation.

The schedule stays fixed, and grows from eight passes to ten (user ruling, 2026-08-30). physics/schedule.hpp states that the eight passes are "fixed at compile time; there is no API to add, remove or reorder one", and that their order is a parity contract because float addition is not associative. Behaviors therefore do not insert themselves anywhere. Two slots are added to the fixed array, and behaviors register into one of them:

  • BehaviorsKinematic — after MediumUpdate, before ForceElements. A pose written here is set before anything reads it, including both collision passes.
  • BehaviorsForce — after ForceElements. Additional wrenches accumulate after the built-in rotors-then-drag order the golden corpus already pins, so behavior forces never perturb the last bits of an existing element's accumulation.

Both slots are always present and inert when nothing is registered — the same pattern the deliberately-inert Gravity slot already establishes. Proof obligation: with no behaviors registered, every existing golden must remain byte-identical, which makes the inertness testable rather than asserted.

Determinism obligations, inherited not renegotiated: no wall-clock; randomness only from the existing per-world, per-system splitmix64 streams under the errata-R4 domain-separation discipline; no allocation inside a step; structural effects queued to step boundaries. The schedule remains data, and a behavior cannot reorder itself or another pass.

GPU: a behavior with no record_gpu is CPU-only and must declare itself so. A world containing a CPU-only behavior is not eligible for the GPU-authoritative path, and this is a refusal, not a silent fallback — the parity corpus must never be able to include a world whose behavior did not run identically on both backends.

Cost if wrong: if the declared read/write sets turn out too coarse, behaviors serialize more than necessary — a performance cost, not a correctness one. The reverse error, permitting undeclared access, would be silent divergence, which is why the declaration is mandatory rather than advisory.

The first behavior closes a blocker in two other programs

The natural first behavior to build is a kinematic mover: a declared pose update applied at a step boundary, deterministic in (seed, tick). That is precisely the capability demo-mission Phase 1 and the tracking-moving-target training structure are both blocked on today — the engine has no mover concept at all, BodyState::flags' kinematic bit is unassigned, and integrate_bodies() is the only thing that moves anything. This spec does not adopt DM3's mover/Target schema, which stays that addendum's to define; it provides the engine mechanism that addendum has been waiting for.

SL7–SL9 — The v1→v2 transfer audit

v1 may not be quarantined while it is the only implementation of anything. The D10 strangler has been running since S1 and was never audited for completeness; this section is that audit, and it found a real gap.

SL8 · SPH fluid is implemented to v2 discipline, not ported

v1's fluid is a pair of GPU-only compute shaders with no CPU path, no determinism story, and no parity obligation. v2 admits no such pass. The transfer therefore means implementing a fluid solver under the engine's existing rules: a declared pass with both execute_cpu and record_gpu, identical math and operation order, fp32 on both, seeded from the domain-separated streams, participating in the golden-corpus parity comparison with its own ratified tolerance band.

This is the largest single item in the program and it gets its own phase and its own checkpoint (§10). It is scoped as: neighbour search reusing the existing sorted grid rather than a second spatial structure; density and pressure-force passes; a Fluid component carrying the material parameters; and the parity band measured, never assumed.

Cost if wrong: if SPH cannot reach an acceptable CPU↔GPU band, the honest outcome is a CPU-only fluid declared under SL6's rule — visible in the sandbox, excluded from GPU-authoritative worlds — not a widened band. Widening a parity band to accommodate a new pass would compromise the corpus for every existing one.

§6

SL10–SL13 — The sandbox

spade_sandbox is the engine's reference application: the place a physics or rendering change becomes visible rather than inferred from an assertion. It replaces spade_viewer and its v1 bridge entirely.

SL10 · the same-path invariant

The sandbox renders through the same spade::render entry points the C5 host and the conformance tests use. There is no second render path, no sandbox-only shading, and no "close enough" preview mode.

Why it is stated as an invariant rather than a preference: the sandbox's entire value is that a visual difference implies a real difference. A private render path makes it a picture of itself, and a tool that can disagree with the tests is worse than no tool, because it will be believed. Guarded by construction — the sandbox links spade::render and SL2b forbids it reaching anywhere else.

SL11 · presentation stack

The CPU rasterizer produces a BGRX8 frame; the sandbox uploads it as a texture and draws one fullscreen quad; ImGui runs on its OpenGL3 backend. The window presents a buffer and hosts a UI — it is not a renderer.

This sits behind a Presenter interface so S7b substitutes Vulkan presentation without touching a line of sandbox logic. GLAD is not reintroduced: ImGui's OpenGL3 backend has bundled its own loader since v1.87, and the vendored pin is v1.91.5-docking. This must be verified against the pinned tag at implementation; if it does not hold, the fallback is the Vulkan presenter using the already-unconditional Vulkan-Headers and volk, not a return to GLAD.

SL12 · the sandbox is object-centric

The UI is organised around SL4's model, which is what makes it an engine editor rather than a scene viewer: a scene hierarchy; a per-object inspector listing attached components with editable configuration; add-object and add-component menus; and an asset browser over the SDF prefab kit, the parametric mesh library and the material palette.

Live controls: CPU ↔ Vulkan backend, switchable on a running scene and runnable side-by-side in lockstep so a parity divergence can be watched rather than read from a JSON file · render mode and shading (shaded, wireframe, raymarch, velocity per SL9c, and a raster-vs-raymarch difference view) · sun direction, sky, exposure, shadows and per-object material · gravity, timestep, substep count and contact parameters.

Inspection: physics debug draw — contact points and normals, body AABBs, the broadphase grid, force and velocity vectors — extending the existing depth-biased overlay path rather than adding one · pause, single-step and scrub with snapshot save and restore on the existing kSnapshotVersion machinery · SDF slice and distance-field visualisation.

SL13 · scene sources and persistence

Three sources behind one picker: curated presets (including §7's successors to the retired scenes) · test scenarios, surfaced in a dev mode through the existing ScenarioData loader so any failing case can be opened and watched · saved sandbox scenes.

The sandbox saves its own scene format (JSON; nlohmann/json is already a dependency), screenshots, and physics snapshots. It does not write .world.yaml or Kat recipes. Canonical content authoring stays where it is; a second authoring home for production content is exactly the outcome this clause exists to prevent.

§7

SL14 — v1 quarantine and scene equivalence

SL14a · quarantine, not deletion

spade/src/, spade/include/, spade/examples/, spade/assets/, engine/tools/viewer/ and the SPADE_BUILD_V1 option move to spade/legacy/ as pure renames with zero edits, following the repo's existing quarantine precedent exactly. GLFW and ImGui move from the SPADE_BUILD_V1 gate to SPADE_BUILD_SANDBOX; GLAD leaves the build entirely.

Location: inside spade/, not the repo-root legacy/. Root legacy/ is a Kat concept, and Spade's own history belongs to Spade — SL1's identity claim would be hollow if the engine's predecessor were archived as a Kat artifact.

"Completely cut off" is enforced, not asserted: no build wiring references it, no target links it, no test includes it, and a ratchet guard in the shape of the existing legacy-quarantine test fails if anything reaches back in.

One thing must be harvested before the viewer moves: engine/tools/viewer/scenes.cpp is v2 code, not v1 — only bridge.cpp touches the old engine. Its eight scene constructors are the direct source material for the eight successors in SL14b and are ported forward, not re-derived from screenshots.

SL14b · scene equivalence, and the order it must happen in

The retired scenes need successor presets that exercise the same objects, physics and rendering — not numerically exact reproductions. Equivalence is judged on three axes, and the axes are not uniform across the eleven scenes, so the spec states each honestly rather than promising one comparison for all of them.

The binding constraint is ordering. Baselines can only be captured while v1 still builds. Once it is quarantined and cut from the build, it can never be run again and the comparison becomes impossible forever:

characterise what each scene exercises
  -> capture baselines from the LIVE v1 tools     <- last moment this is possible
    -> build the successor presets
      -> compare on all three axes
        -> only then quarantine

The two populations

The eleven scenes are not one set. The eight spade_viewer scenes — drop · bounce · shower · gate · hover · wind · flight · swarm — already run v2 physics and are merely rendered through the v1 bridge. The three Sandbox.exe scenes — fluid (50,000-sphere SPH), spheres, cubes — run v1's own engine, which is the thing being retired.

SL14c — fluid becomes a standing capability target

The 50,000-body scene is the largest stress case in the tree and is retained as a permanent preset and a stated sandbox requirement, not merely as a migration artifact. The three v1 successors are labelled as capability demonstrations, never as parity or regression claims, so that no later reader mistakes them for a numeric guarantee they cannot support.

§8

SL15 — Build, CI, and how a windowed tool gets tested

SL15a · build gating

A new SPADE_BUILD_SANDBOX option, default ON, which CI configures OFF — the same pattern SPADE_BUILD_V1 uses today and that CI already exercises. The reason the windowing dependencies were gated in the first place is recorded in the vendor file and still applies: a bare Linux runner has no X11/Wayland development packages, and FetchContent_MakeAvailable(glfw) fails its own configure without them.

SL15b · headless is the test surface

spade_sandbox --headless loads a scene, applies options, steps, renders and dumps frames with no window, feeding the existing frame-dump and golden-image pattern. Every panel's logic is reachable from it, and it runs in CI with the window build off.

The window itself is a deliberately dumb shell: presentation and input, nothing else. Any logic that migrates into it is a defect, because it becomes untestable by construction. This is the concrete answer to "how does a GUI tool avoid regressing silently" — by having almost nothing in the GUI.

Hosted CI is presently failing on a billing block rather than a quota, so every claim in this program is proven on local evidence under the standing directive until that is resolved. That is a condition of the environment, not of this design.

§9

SL16 — Vocabulary

SL16 · "component" is shared and context-scoped (user ruling, 2026-08-30)

Both Spade and Kat keep the word component. They are the same idea — a part attached to an underlying structure — and the trees are worked separately, so context disambiguates in practice.

Two things make that safe rather than merely convenient. In code the namespaces already separate them: Spade's are C++ types under spade::; Kat's are C3-contract manifests addressed by dotted typeId strings such as decision.policy. And AGENTS.md's vocabulary section records that both senses are live and context-scoped, so a reader meeting the word at the dronesim/spade/ boundary — the one place both appear in a single file — knows there are two.

Not renamed: element stays the force-element layer's word (rotors, drag surfaces) in Spade, and is not a synonym for a component in either tree.

§11

SL18 — Verification

  • The object graph does not perturb physics — an existing golden scenario produces bit-identical results with and without an object graph built over it. This is the SL3 claim, tested rather than argued.
  • Snapshot compatibility — a snapshot taken before P1 restores after it, unmodified.
  • Behavior determinism — a world with a behavior produces identical trajectories across runs, processes and backends; a CPU-only behavior is refused from the GPU path rather than silently degraded.
  • SPH parity — measured band with recorded provenance, never widened to accommodate a result.
  • Transfer completeness — a guard asserts every SL7 register row is dispositioned, so a future v1 system cannot be quarantined unnoticed.
  • Public-surface purity — the sandbox's include graph touches only installed headers (SL2b).
  • Standalone consumption — the out-of-tree find_package(spade) consumer builds and runs with SPADE_BUILD_SANDBOX=OFF and no GL anywhere.
  • Quarantine ratchet — a seeded violation reaching into spade/legacy/ fails the guard.
  • Scene equivalence — the eight v2 successors assert bit-identical trajectories; all eleven carry pinned golden frames going forward.
Guard discipline carried from the render program

A constant, test, or fixture validated only against something that cannot vary is unvalidated. That lesson was learned six times over in the 21st spec's execution. Every guard this spec adds must be shown to fail under the mutation it exists to catch — the transfer-completeness guard with a row removed, the quarantine ratchet with a seeded reach-back, the purity guard with an internal include, the equivalence assertions with a perturbed trajectory.

§12

What this spec does not do

  • Extract Spade to its own repository. Hardening in place; extraction is a later decision with a stated trigger, not a deliverable here.
  • Author canonical content. The sandbox saves its own scenes and never writes .world.yaml or Kat recipes.
  • Build the full ECS. Queries, signature iteration and archetype storage are designed against, not implemented.
  • Scripted or plugin behaviors. SL6 admits declared, compiled, deterministic behaviors only.
  • Adopt DM3's mover/Target schema. P2 supplies the engine mechanism; the schema stays that addendum's to define.
  • Vulkan presentation, camera sensors, the ImGui debug HUD on the GPU path. S7b's, behind SL11's Presenter seam.
  • Change the C5 ABI. Untouched. Phase G remains its only amending authority.
  • Textures, PBR, post-processing, mesh colliders. Unchanged from the 21st spec's exclusions; SDF remains collision truth.
  • An ABI or API stability promise. Seat S1's, if ever wanted.
