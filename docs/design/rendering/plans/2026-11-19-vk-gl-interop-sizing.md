# Vulkan-to-GL volume interop: sizing (Rendering, 2026-11-19, for KAT D180 "run smoother")

Half a page, no code. Question: what would it take for GL to draw the GPU airflow's published volume without a CPU round trip, and is it worth it?

**Today (airflow design Q7, option A).** Vulkan solves and publishes (`publish_fields` 6.21 ms, `pack_f16` 1.10 ms at the D1 box, 224x168x160 = 6.0 M cells), then the f16 halves are READ BACK to the host (16.2 ms of 109 MiB, measured 2026-10-26, RTX 3060 Ti, `GpuAirflowPublish.P8ReadbackCostAtTheD1Box`), become a `FlowVolume`, and GL UPLOADS them to 3D textures once per generation. GL's upload is measured only at 128^3 (32 MB): 5 to 8 ms per upload (`FlowViewsCostCachedAndUncached`, 2026-10-19). Scaled to 109 MiB that is roughly 17 to 27 ms (an ESTIMATE, not measured at the D1 box). So the transfer costs about 33 to 43 ms a frame against about 7 ms of device work: at 30 fps (33 ms) option A cannot fit; interop removes nearly all of that transfer.

**What interop is (option B).** Windows first: Vulkan allocates the halves buffer with `VK_KHR_external_memory_win32` and exports a handle and a semaphore (`VK_KHR_external_semaphore_win32`); GL imports them with `GL_EXT_memory_object_win32` and `GL_EXT_semaphore_win32` (`glImportMemoryWin32HandleEXT`, a buffer on that memory, `glWaitSemaphoreEXT`/`glSignalSemaphoreEXT`), then fills the 3D textures from the buffer on the device (a device-to-device unpack, under 1 ms at these sizes, estimate). Nothing crosses PCIe. Linux later with the `_fd` variants. Both contexts must be on the same physical device (match the LUID).

**Work, by realm.**
- Core/Physics (the Vulkan runner): allocate the published halves exportable, return the handle and a signal semaphore each publish. About 2 to 3 days with a gated test.
- Rendering (GL): an import call on `GlRenderer` (memory and semaphore handles, the volume's dimensions), a per-frame wait, unpack and signal, and a "device-resident" `FlowVolume` (header only, no host arrays) that `GlRenderer::draw` marches and the CPU renderer refuses by name. It touches `validate_flow_volume`, the generation cache and every view of the volume. About 3 to 4 days with RED tests, plus the first debugging of cross-API sync.
- Anything on the host that reads the volume (streamlines, probes, tracers, the editor's CPU views) still needs a host copy: either a second, rarer readback, or those views stay on the old path.

**Risks.** Driver and extension availability (the NVIDIA driver here has them; unverified on other vendors); synchronisation bugs that show as torn or one-frame-old volumes; tests that can only run on a box with both APIs (the Linux leg would skip them); and a hard dependency between two realms' code.

**Cheaper first (no new API).** The readback and the GL upload do not have to be serial: pipeline them (a PBO ring for the upload, the next publish running while the last volume uploads), at the price of one frame of display latency. That caps a frame at the slowest stage (about 20 ms, estimate) instead of their sum (about 40 ms), for roughly a day's work, and `GpuGlRenderer.ReadbackCostSyncAndPboRing` already measures the pattern. Recommendation: pipeline first and measure at the D1 box (also measure GL's upload there, which I have not); build interop only if that still misses the budget. If the owner wants 60 fps at the D1 box, interop is the only route.
