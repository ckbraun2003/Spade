# The test-class floors, as downtime tickets (2026-11-22)

What is pending (tests/bench/PERF.md, "The first baseline"): the **test-class floors**, on `real_time`, for the test-class metrics (9 in the registry: eight Google Benchmark programs through `{bench}` and `interface.startup_version` through `{sandbox}`), from two runs of one SHA. The gpu-class floors are in `floors.json`. This plan takes them in the crew's Night. The SHA is a placeholder, `<sha7>`: batch 50's code (e63b0978) once the lead confirms gate 50 passed, or another the lead names. Nothing here is queued, cloned or built until the lead confirms the SHA and Oversight has answered on the clone (section 1).

## 1. What the harness insists on, and how each is met

- **`--tree` is a checkout whose HEAD equals `--sha` and has no uncommitted change; it is never written to.** There is no Test/Docs worktree (removed, O179). The measured tree is a **local clone** of the main checkout's path, in the scratchpad (`SP/perf/tree`), made by `git clone --no-checkout` (no network) and `git checkout --detach <sha7>`, then **`git remote remove origin`**, so the clone has no fetch or push target at all (the script checks `git remote` prints nothing, or stops); **nothing is ever fetched into it**. A tree that already exists (a second night) is checked (HEAD starts with the SHA, clean, no remote) and reused, else the script stops; the script never deletes it. It is removed after the floors land only by a literal line the lead relays, and its size is printed when it is made. The build directory is ignored by git (`build-*`), so the tree stays clean. Oversight allowed the clone on these conditions (2026-11-22).
- **The build is the gate's binary.** The configure is `cmake -S <tree> --preset msvc-ninja-release` (what `scripts/build.ps1 -Preset release` runs, with the same `find-python.ps1` Python), and **only the dependency source differs**: `-DFETCHCONTENT_FULLY_DISCONNECTED=ON` and `-DFETCHCONTENT_SOURCE_DIR_<DEP>=<main checkout>/build-ninja/release/_deps/<dep>-src` for each of the 13 dependencies, read-only (nothing is written there). A dependency missing from that root **fails the configure**: `build-tree.ps1` checks each folder exists first and stops naming it, and the disconnected flag stops CMake itself from fetching. The fc build's `-DSPADE_BUILD_V1=OFF` is not used: the floors must measure the gate's flags. Then `scripts/build.ps1 -Preset release -Target spade_bench` and `-Target spade_sandbox`, the two programs the test-class metrics run.
- **The harness runs from a scratch copy** of `tests/bench` from master (`git archive`), not from the measured tree, with `--ledger`, `--env` and `--floors-file` on scratch copies of master's files, so neither the measured tree nor the main checkout is written. The new rows reach the repo by a plumbing commit onto a branch, as before.
- **The box must be quiet.** The harness's own guard stays: it waits up to 10 minutes for under 5% CPU over 10 s, reads `job status` before the first run, after each repeat and at the end, and marks a run noisy if another heavy, gpu or quick job appears. A noisy run is never in a median or a floor: the floors step reads the last two `environment.csv` rows and refuses unless both are of the SHA with `noisy` 0; a noisy night is reported and the runs queued again for another night.
- **Downtime tickets** (`vantage.py queue --downtime`) run when Cameron starts the crew's Night. The command takes `--class` and `--limit-s`, not `--expect-s`.

## 2. The tickets (SP = this session's scratchpad folder; scripts in `SP/perf`)

1. `python %USERPROFILE%\Desktop\Vantage\vantage.py queue --downtime --ticket spade-testdocs-perf-build-<sha7> --class build --limit-s 7200 --cwd SP/perf -- powershell -NoProfile -ExecutionPolicy Bypass -File SP/perf/build-tree.ps1 <sha7>`: the clone, the gate's configure with the deps root, the two targets; on success `build-ok-<sha7>.txt` holds the full SHA.
2. `... queue --downtime --ticket perf-<sha7>-1 --class test --limit-s 2880 --cwd SP/perf -- bash SP/perf/run-measure.sh <sha7> 1`, and the same with `-2` (two runs of the SAME SHA, for the floor). Each exits 3 with "build did not pass; nothing measured" if the marker is missing or names another SHA, so a measure starts only if the build passed, whatever order the night runs them in; otherwise it runs `python -I SP/perf/bench/measure.py --sha <full sha> --tree SP/perf/tree --build-dir build-ninja/release --class test --out-json SP/perf/<sha7>-<n>.json` with the scratch ledger files.
3. `... queue --downtime --ticket perf-<sha7>-floors --class test --limit-s 600 --cwd SP/perf -- bash SP/perf/run-measure.sh <sha7> floors`: `measure.py --floors <sha7>-1.json <sha7>-2.json --out-floors SP/perf/floors.json`, only if both result files exist and `check_two_runs.py` finds both environment rows clean and of the SHA (else exit 5).

## 3. Times

- The 2026-11-16 baseline measured the suite in quiet windows of **10 to 20 minutes per pass** (pass A 01:30 to 02:05 and pass B 07:30 to 08:05 each held three jobs, T, G1 and G2; the ledger holds no per-job seconds). The T job is one of the three, so 20 minutes is its ceiling. A downtime ticket has no `--expect-s`; the measure limit is 2 x (20 min x 1.2) = **2,880 s**, and the measured seconds go into the record after the first night.
- The build: no measured time for a clean Release build of these two targets in a fresh tree; the limit is **7,200 s** (class build, long), and the measured elapsed goes into the record after the first night.
