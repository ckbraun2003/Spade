# Test/Docs: tests, cadence and run-folder checks for the flight computer and autopilot links (phase 0)

**Owner:** Test/Docs. **Status:** phase 0 proposal, docs only, for the lead's review. On Cameron's word (O140, 2026-11-21): a real autopilot (PX4, then ArduPilot) flies Spade's X500 in lockstep under a simulated companion computer. The map is Oversight's `2026-11-21-full-sim-flight-computer.md`, "Phases and test cycles". Core's, Physics' and Interface's sections land beside this one in their own libraries.

Every bar below is a proposal. Under `TD-2` a bar is fixed before its first run and moves afterwards only by a recorded decision, so review is where they get argued. A figure marked *(estimate)* has not been measured; one that cites a record is that record's.

## 0. How to read it

**Four kinds of test**, because they cost and fail differently:

| Kind | Needs | Runs in | Label |
|---|---|---|---|
| Unit and replay: messages, frames, sensor statistics, the Spade-side replay, budget-mode arithmetic, the run-folder checker | Spade alone | the ordinary suite, so also the Docker gcc leg | `spade` |
| Link and flight: lockstep, scripted flight, the live repeat, the mutation set | the autopilot SITL running | their own job, `ctest -L fc` | `fc` |
| Measured-mode caps | Windows Job Objects, a child process | their own job | `fc` |
| Sweeps | the autopilot, many runs | the queue's downtime | `fc` |

Proposed `TD-17` (not signed): **the `fc` label.** Like `step` (`TD-16`), an `fc` test carries `fc` and not `spade`, so `scripts\test.ps1` and the Docker leg (`-L spade -LE gpu`) leave it out with no script edit. An `fc` test that cannot find the autopilot image fails (`TD-5`); it may skip only for the named absence "no autopilot image", and the skip is reported by name and does not count toward green on the development box (`TD-13`'s reading).

**What these tests cannot show.** A repeat test shows reproducibility, not correctness (`01-verification.md`, "What a determinism test cannot see"). A flight that holds 5 m shows that PX4 flies the model Spade built. It does not show that the model is the real X500; that is phase 6, against flight logs. The run report says the flight controller's own compute is not modelled (the map, piece 1), and a test asserts the report says so (check K9).

**Assumptions I make about the other realms' sections** (each is repeated in section 6 as a question):

- **A1.** One *link step* is one autopilot step: PX4's sensor rate, 250 Hz, so 4 ms of simulated time. How many Spade ticks that is (one at 4 ms, or four at 1 ms) is Core's and Physics' call. My bars count link steps and say nothing about substeps.
- **A2.** Spade's world is y up, and one fixed table maps it to the autopilot's NED world and FRD body frames (section 1, FC-U2). Core owns the table; the vectors below pin it.
- **A3.** The Spade trace is one record per link step: the step index, the simulated time in microseconds, the state digest (the FNV-1a fold over the state registry's walk that `replay.hpp` uses), and a hash of each message that crossed the link in that step. With the message hashes in it, the trace is the whole interface, and a Spade run is a function of the seed, the world and the actuator stream alone.
- **A4.** PX4 facts below (HIL_SENSOR, HIL_GPS and HIL_ACTUATOR_CONTROLS over TCP 4560, in lockstep; the log is a `.ulg`) are recalled from its documentation, not checked here. Phase 1's first task is to check each against the pinned release, and a bar that rests on one says so.

## 1. Test cycles and pass bars

### Phase 1: PX4 flies the X500, no Kat

#### FC-U1. Messages (unit, `spade`)

- **Golden vectors, one per message the link sends or reads:** HEARTBEAT, HIL_SENSOR, HIL_GPS, HIL_ACTUATOR_CONTROLS, and the few the harness uses to command the flight (COMMAND_LONG for arm, take-off and land; COMMAND_ACK; the landed-state report).
- **Bar:** `encode(decode(v)) == v` byte for byte for every vector, including MAVLink v2's truncation of trailing zero bytes and the CRC with its per-message extra byte. `decode(encode(m)) == m` for 1,000 seeded random messages per type, floats compared by bits (a NaN payload survives).
- **Refusals, each named and each its own case:** bad magic, bad CRC, length that disagrees with the header, a truncated frame, an unknown message id with a good CRC (skipped and counted, never an error), a length over the maximum.
- **RED first:** each decode case is written against a stub that returns "no message", and each refusal case against a corrupted vector, so every case is seen to fail before it passes.
- **Where the vectors come from (`TD-4`):** not from our encoder. The recommendation is bytes captured from the real PX4 container in phase 1, which PX4 itself sent and accepted, pinned with their provenance (release, command, date). The alternative is a reference generator (pymavlink at a pinned version), which is a download for Cameron's OK. The per-message CRC extra bytes come from the message definitions in PX4's own tree, once, after the PX4 fetch the map already lists.

#### FC-U2. Frame conversions (unit, `spade`)

- **A signed-permutation conversion is exact.** Position, velocity, force and the body axes between Spade's y-up world and NED and FRD are signed permutations of the components, which floating point does exactly. **Bar: bit-equal**, for the 24 proper rotations of the cube applied to the attitude and for the three axis vectors each. A conversion that is not a permutation (a motor's install turn that is not a multiple of 90°) is within 2 ulp.
- **Meaning vectors, derived by hand, not by the conversion code:**
  - level at rest: the accelerometer reads +g up, which in FRD is `zacc = -g` (`-9.80665 m/s²`), `xacc = yacc = 0`;
  - pitched nose up 90°: `xacc = +g`;
  - rolled right wing down 90°: `yacc = -g`;
  - turning counter-clockwise seen from above at ω: `zgyro = -ω` (a turn about up is a turn about down with the sign reversed).
- **Bar on the vectors:** within 1e-6 relative at fp32.
- **GNSS origin.** Spade's GNSS has no datum (`03-sensors.md`), so the link owns the origin. The conversion to degrees times 1e7 and back stays within 1.2 cm (a half step of 1e-7 degree is 0.56 cm) over ±5 km, against a double-precision reference written in the test. The projection PX4 uses is recalled, so a vector pins it once phase 1 reads the source.

#### FC-U3. Sensor statistics (unit, `spade`; the sensors are Physics', the tests are mine)

Every sensor is run alone, on a body at rest, so a million samples take seconds, and **every case has a pinned seed**, so a pass is a pass for ever and nothing flakes. The bars come from sampling theory and are fixed now:

| Sensor | What is checked | Bar |
|---|---|---|
| IMU gyro and accelerometer (exist) | sample mean; sample standard deviation; Allan deviation at three averaging times against the closed form for the row's noise density and bias walk; the density scaling (run at 250 Hz and at 500 Hz: the Allan deviation at the same averaging time is the same) | mean within 5σ/√N of the bias; deviation within 5/√(2N) relative (±0.8% at N = 200,000); Allan within 10% of the closed form at N = 1e6 |
| GNSS (exists) | the Gauss-Markov bias: stationary deviation and lag-1 autocorrelation `e^(-dt/τ)`; the white part | deviation within 5%; autocorrelation within ±0.02; N = 100,000 fixes (sensor-only, so cheap) |
| Barometer (new) | pressure against the International Standard Atmosphere table at 8 altitudes, noise off; the noise deviation; the bias walk | within 0.1 Pa (about 1 cm); the other two as the IMU |
| Magnetometer (new) | the world's field rotated into the body at 24 attitudes: its length, and its direction against hand vectors; the noise; a hard-iron offset when the row declares one | length within 1e-6 relative; direction as FC-U2; noise as the IMU |
| All | the sample count over 100 s is the rate times 100 exactly (a sensor sample is never shed under load, `03-sensors.md`); the same seed gives byte-equal samples; two sensors' noise streams are uncorrelated (|ρ| < 5/√N); the GPU backend's draws sit inside `CORE-3`'s band | exact; exact; as stated; as `CORE-3` |

The barometer and magnetometer tests are written first and fail as `absent:` until Physics' rows land (`TD-5`). The engine takes no libm (`TD-3`), so the barometer's atmosphere has to use `fp32_math`; the reference table is in double and independent of it.

#### FC-L1. The link test (`fc`)

- **What runs:** 10,000 lockstep link steps (40 s of simulated time) against PX4 at its pinned release, with the X500 at rest on the ground, noise on, armed or not.
- **A gap is any of these, and one fails the test:**
  - a link step with no sensor message sent, or two;
  - a link step whose actuator reply did not arrive before the next step began (Spade never advances before the reply; the wait has a wall-clock timeout of 5 s *(estimate)* that fails the test);
  - a simulated time that does not advance by exactly the step (4,000 µs) between consecutive messages;
  - in the PX4 log, a `sensor_combined` timestamp difference other than the step *(to be checked against the pinned release, A4)*;
  - a count of sensor messages that differs from the count of steps, in the trace or in PX4's own log.
- **Fault cases, each RED first:** the autopilot stopped mid-run (the container paused): Spade does not advance, and the test fails with a named "autopilot silent at step N" inside the timeout, never a hang. The autopilot killed: named refusal. A malformed reply: skipped and counted as in FC-U1, and the run fails if the count is above zero.
- **Soak, nightly:** 250,000 steps (1,000 s), same bars.

#### FC-F1. The scripted flight (`fc`)

The script: arm, take off to 5 m, hold 60 s, land, disarm. No wind. It runs twice: **F1a with every noise model off**, which isolates the link and the conversions, and **F1b with the X500's default sensor models on**, which is the flight that counts. A failure of F1b alone points at the noise or the estimator; a failure of both points at the link.

The map's bars hold, and I refine them in three places:

1. **Altitude is judged on Spade's truth, not the autopilot's estimate (`TD-4`).** An estimate that is wrong by 5 m (a barometer bias) would hold its own altitude perfectly and pass a test that reads the estimate. So:
   - **Truth within ±0.3 m of 5 m for the whole hold** (the map's bar, kept).
   - **The autopilot's estimated altitude within 0.3 m of truth** across the hold: this is the check that catches a wrong sensor.
2. **The hold window is defined.** It starts at the first step after the truth has stayed inside ±0.3 m of 5 m for 2 s, and lasts 60 s. Take-off must reach that point within 20 s of the command, or the flight fails as "never reached the hold".
3. **More than altitude.** My a-priori additions, which the map does not have and which review should confirm:
   - horizontal position within ±1.0 m of where the hold began;
   - speed under 0.5 m/s and tilt under 5° in the hold;
   - touchdown vertical speed at or under 1.0 m/s, and the autopilot reports disarmed within 10 s of touchdown;
   - Spade's invariants hold throughout (no NaN, no body inside a solid), and the body touches the ground only before take-off and after landing.

**"No estimator failsafe" and "a clean PX4 log", made checkable:**
- the log's failsafe flags are clear at every sample;
- the estimator's innovation test ratios stay under 1;
- no log message at ERROR level or above, except entries on a short **allow-list that starts empty**, each entry added with its reason beside it (as a band's margin is, `TD-2`).

**Phase-1 flights cost** *(estimate)*: 25,000 link steps, about 100 s of simulated time.

#### FC-R1 and FC-R2. The repeat tests

The map's one test hides two questions: is *Spade* repeatable, and is *PX4 in lockstep* repeatable? If PX4 changes one output by one bit, Spade's trace differs, and that is not a Spade failure. So:

- **FC-R1, Spade's replay (`spade`, no autopilot).** The link records the actuator stream of a run (`actuators.bin`). Replaying that stream into Spade, with no autopilot, must reproduce the trace **bit-equal at every step**, not only the last. The test needs no PX4: it runs in the ordinary suite from a seeded, generated actuator stream (hover trim plus a seeded perturbation), with the final trace digest **pinned as a golden under `TD-1`**. **The Docker gcc leg must reproduce the digest (`TD-12`).** This is the strong claim, and it is cheap: it puts the link's Spade side under both toolchains with no autopilot.
- **FC-R2, the live repeat (`fc`).** The same seed twice, in two processes and two fresh containers. **Bar: the Spade traces are bit-identical at every step.** The test also writes `repeat-diff.md`: the first differing step, and the PX4 log differences by topic and first differing timestamp, apart from fields on a reasoned wall-clock or process-id allow-list.
- **If PX4 turns out not to repeat**, the bar becomes bands on the hold's statistics (mean and spread of altitude, horizontal drift, estimator innovations), measured over 20 repeats and then pinned with margin (`TD-2`). That decision is recorded after the measurement and is not made now.

### Phase 2: the Kat package on the simulated companion computer, budget mode

Spade builds the board profiles and the compute model; Kat's `kat_deploy` is what runs on it. The bars on Spade's side:

- **FC-B1. The arithmetic is integer microseconds.** A component's cost per tick on a board is the declared cost times the board's speed factor, rounded once, in integers. No floating-point accumulation, so the same seed gives the same count on every toolchain.
- **FC-B2. Overruns, RED first.** One component, tick period `P`, cost `C`:
  - `C = P/2`: zero overruns, and the sensor-to-motor latency is exactly `C` rounded to the step;
  - `C = P` exactly: zero overruns (the boundary is "over", not "at");
  - `C = P + 1 µs`: one overrun every tick;
  - `C = 1.5 P`: an overrun count equal to the count worked out by arithmetic in the test from the profile (`TD-4`), not read from the meter.
  - Each is written to fail against a model that adds no latency.
- **FC-B3. The speed factor scales exactly.** A profile at twice the factor doubles every cost, with no rounding error beyond one microsecond.
- **FC-B4. A too-slow profile trips the package's failsafe** (the map's bar, RED first): the meters show misses, the failsafe trips, and the step where it trips is the same in every run.
- **FC-B5. The same seed gives the same outputs, trace and overrun count**, bit-equal, and the Linux leg reproduces the overrun count (`TD-12`) because it is integer arithmetic. The flight bars of F1b are re-run through a package: the 6-gate course (exact state, then estimated state) and the hover box.
- **FC-B6. The meters are present and recounted.** Compute per tick, deadline misses, memory peak and sensor-to-motor latency exist, are finite, and the miss count equals a recount from the per-tick costs in the run folder (check K6).

### Phase 3: measured mode, job-object caps

Results here vary, so **no test pins a measured number**. The bars are properties, each with a margin, and every figure printed carries its box and tree (`TD-8`).

- **FC-M1. The CPU rate cap holds.** A busy child under a 10% cap uses 7% to 13% of the wall time over five 10 s windows (the median), measured on this box *(the width is an estimate; the first measurement fixes it under `TD-2`)*.
- **FC-M2. Affinity holds.** A child with four busy threads and two cores used never exceeds 2.1 cores of CPU time per second of wall time.
- **FC-M3. A memory cap below the package's peak is a named refusal.** The host reports `memory_cap_exceeded`, naming the cap and the peak, writes the run record, and stays up. A crash of the host fails the test.
- **FC-M4. Starvation trips the failsafe, and ample does not.** At a cap at or under half of what the package needs, the failsafe trips in 20 of 20 runs. At twice what it needs, it trips in 0 of 20. The middle is not tested, since a boundary case is flaky by nature. Both counts are reported with the spread of the trip time.

### Phase 4: scenarios at scale

Gusts, sensor noise and bias, GPS loss, link loss and latency, battery sag, compute starvation, as nightly sweeps. A flight that ends in a landing is not a failure of a GPS-loss run, so a sweep's bar is not "every flight passes":

- **Each scenario declares its expected outcomes** (for GPS loss: the autopilot reports the failsafe within a stated time, then lands or holds, by the scenario's setting). An outcome outside the set is red; one inside it is data.
- **The sweep passes** when every run folder passes the checks of section 3, every run's trace digest reproduces for a 10% sample re-run, and the signed report is written.
- **Scale is bounded by cores, not by Spade.** PX4 is one process per drone, so a sweep's parallelism is the box's 16 threads, shared with Kat's tree, not the 256 worlds the Vulkan record measures. Sweeps are sequential or a handful wide *(estimate)*.

### Phase 5: ArduPilot through the same seam

FC-L1, FC-F1, FC-R1 and FC-R2 are rerun against it with their bars unchanged. FC-B and FC-M do not depend on the autopilot and are not rerun. One bar changes for a reason to confirm: as I recall it, ArduPilot's JSON simulator link takes the vehicle's IMU, position, attitude and velocity from the simulator and makes its own barometer, compass and GPS from them, so Spade's barometer and magnetometer would not reach it (open question 8).

### Mutation set: the flights, RED first

A test that cannot fail proves nothing, and a real flight cannot be made to fail by editing the test. So the flight tests are shown red by breaking the *input*:

| Mutation | What the test must report |
|---|---|
| two motor outputs swapped | F1 fails (never reaches the hold, or flips) |
| a barometer bias of 5 m | F1b fails on the estimated-versus-truth bar |
| one gyro axis sign flipped in the conversion | F1 fails |
| the autopilot's reply delayed by one step | L1 reports the gap |

Run nightly, not per gate, because each is a flight.

## 2. Cadence

| Tier | What runs | Needs the autopilot | Budget *(estimates)* |
|---|---|---|---|
| **Every branch** that touches the link, the sensors, the frame table, the compute model or the autopilot image | FC-U1 to FC-U3, FC-R1, FC-B1 to FC-B3, K-checks on the fixtures (all in the ordinary suite); **and** FC-L1 and F1a | L1 and F1a only | suite: seconds each, and each under the debug 60 s limit, timed under ctest in debug; L1 about 1 min, F1a about 2 min |
| **Every other branch** | the ordinary suite, which already holds the unit, replay and budget tests | no | no change |
| **The lead's batch gate** | the above, plus F1b, FC-R2 (two flights), FC-B4 to FC-B5, and K-checks on a real run folder | yes | about 10 min of flights (L1, F1a, F1b and two for R2), plus a cold daemon (see below) |
| **Nightly, `--downtime`** | the soak (250,000 steps), the mutation set, FC-M1 to FC-M4 with their 20 runs, the phase 4 sweeps, and from phase 5 the ArduPilot reruns | yes | the sweeps run as long as the queue allows; each ticket stays under 900 s so none is a LONG job |
| **Every release** | the evidence pack: the gate's flights as one signed report | yes | |

**The Docker gcc leg gains the unit, replay and budget tests for free** (they carry `spade`), so FC-R1's digest and FC-B5's overrun count meet the second toolchain at every leg. The leg does not run `fc`.

**Where the autopilot runs, and the job class.** I propose **no new job class**. A flight is CPU work with a container beside it, so it queues as `--class test` with `--floor-gb 4` *(estimate; the leg uses 8)*. Spade runs on the host on its CPU backend, which is the golden source (`L4`) and also the faster path for one world (0.002 ms a step against 0.32 ms on Vulkan, `records/2026-11-18-cpu-vs-vulkan-rtx3060ti.md`), so a flight uses no GPU slot. The autopilot is a pinned image run as a container, the way `docker-leg.ps1` does it: a script `scripts/fc-run.ps1` would start `docker-up.ps1` first, run one container per run named for it, and use none of the leg's volumes. The host reaches PX4 on its published TCP port.

- **Tickets** follow the usual rule: `spade-testdocs-fc-flight-<sha>`, with `-fc-` in the name. Never start one with the class or the realm alone.
- **Limits:** the ticket's `--limit-s` is at least 300 s plus the run's own time, because `docker-up.ps1` waits up to 300 s for a cold daemon (`02-build-and-gate.md`, "The daemon"). L1: `--expect-s 60 --limit-s 600`. A flight: `--expect-s 120 --limit-s 600`. FC-R2 (two flights): `--expect-s 240 --limit-s 900`. All estimates.
- **The wall time is PX4's, not Spade's.** At 0.002 ms a step, 100,000 Spade steps cost 0.2 s; the rest is PX4's lockstep and the TCP hop between the host and the container. I have no measurement of either, so my planning figure is 5 times real time *(estimate)*, and phase 1's first run replaces it.
- **Kat quits Docker Desktop when no Spade Linux work is running or queued.** An `fc` job has to count as Spade Linux work, or the daemon is gone under it. That is a request to Kat, through the lead.

## 3. The run folder: what a test asserts about the record

The folder is the map's piece 6: the Spade trace, the autopilot's log, the `kat_deploy` log, the compute meters, the board profile, the package hash and seeds, and one signed report. The checker is **one display-free implementation**, called by the flight tests, the sweeps and a headless test (the rule of `2026-10-19-end-goal-checks.md`, section 0). `absent:` and `mis-staged:` verdicts never pass. Each check is **red first against a fixture folder**: a small synthetic folder in the repo with one thing wrong, so the checker is shown to fail without a PX4 run. These fixture tests are FC-U-class (`spade`).

| | Asserts |
|---|---|
| **K1** | Every required file is present, by name. An absent file is `absent:`, not a pass. |
| **K2** | A manifest lists every file with its size and SHA-256, every file matches, and no file is unlisted. |
| **K3** | The trace's header names the Spade commit, the compiler, the backend, the seed, the step and the scenario. Its record count equals the report's step count. The digest of the per-step digests equals the report's trace digest. |
| **K4** | The autopilot log opens with the `.ulg` magic and parses. Its simulated-time span equals the trace's within one step. Its firmware version equals the pinned release in the report, and its parameter set's hash equals the hash of the X500 parameter file the run was given. |
| **K5** | The board profile's hash equals the report's, and the mode (`budget` or `measured`) is stated. In measured mode the box and the tree are present (`TD-8`). |
| **K6** | The meters are finite and present. In budget mode the miss count equals a recount from the per-tick costs. |
| **K7** | The package hash and the seeds are present, of the right length, and the seeds equal the run's. |
| **K8** | The report's signature verifies. Flipping one byte of any listed file, or truncating one, makes verification fail (red first). What "signed" means is Kat's to say (open question 9). |
| **K9** | The report carries the machine-readable flag `fc_compute_not_modelled` and its sentence, and states which parts are deterministic (the Spade trace, budget mode) and which were measured. |
| **K10** | No user folder name or path appears anywhere in the folder (the same redaction the installer records use, since a report may be shared). |
| **K11** | A replay of the folder's `actuators.bin` reproduces its trace (FC-R1 against a real run). |

Run folders are not committed: they live in a git-ignored folder (`build-fc/<run id>/` in my examples; the name is Core's and Interface's to give). What is committed is the fixtures, the goldens and, per release, the evidence pack's report.

## 6. Open questions

1. **Link step (A1).** Is the link step 4 ms (250 Hz, PX4's usual sensor rate), and how many Spade ticks is it? Core and Physics.
2. **Which downloads.** For the PX4 SITL image: the pinned release, its source and toolchain, and the base image. The flight bars cannot start until Cameron says yes; the message vectors need nothing else after it.
3. **Where Spade runs.** On the Windows host with PX4 in a container (my proposal: it is the box's real configuration), or in the leg's Linux image beside PX4 (no TCP hop through Docker Desktop, and a gcc trace). I propose the first for the gate and the second as a nightly cross-check: **the two traces for the same actuator stream must be identical**, which is `TD-12` for a flight.
4. **Does PX4 in lockstep repeat bit for bit?** Unknown until phase 1 measures 20 repeats. FC-R2's bar waits on it, and FC-R1 does not.
5. **A priori horizontal and tilt bars in F1.** ±1.0 m, 0.5 m/s and 5° are mine. Confirm or replace them before the first run.
6. **A new job class or not.** I say `--class test --floor-gb 4`. Vantage's owner may prefer a class that counts the autopilot's cores.
7. **Docker quitting under a flight.** Kat must count an `fc` job as Spade Linux work.
8. **ArduPilot's sensors (phase 5).** Confirm from its documentation, once fetched, which sensors its JSON link takes from the simulator. If only the IMU and the state, then Spade's barometer and magnetometer tests stay but do not reach ArduPilot, and phase 5's noise scenarios change.
9. **"Signed".** What signs the report, with what key, and who verifies it. Kat's; check K8 waits on the answer.
10. **How wide a sweep is** in phase 4, given 16 threads shared with Kat's tree, and whether a sweep may use more than one PX4 at a time.
11. **The wall time of a lockstep flight.** My 5 times real time is a guess. The gate's budget in section 2 moves with it, and a slow lockstep may force the flights out of the gate and into the nightly tier.
12. **Does Physics keep one world per drone in a sweep?** Batching many drones in one Spade world step would change the trace's meaning (A3).
