## 0. How to read it

**Four kinds of test**, because they cost and fail differently:

| Kind | Needs | Runs in | Label |
|---|---|---|---|
| Unit and replay: messages, frames, sensor statistics, the Spade-side replay, budget-mode arithmetic, the run-folder checker | Spade alone | the ordinary suite, so also the Docker gcc leg | `spade` |
| Link and flight: lockstep, scripted flight, the live repeat, the mutation set | the autopilot SITL running | their own job, `ctest -L fc` | `fc` |
| Measured-mode caps | Windows Job Objects, a child process | their own job | `fc` |
| Sweeps | the autopilot, many runs | the queue's downtime | `fc` |

**The `fc` label** (the lead's phase 0 ruling; recorded as `TD-17` when the label lands, section 5): like `step` (`TD-16`), an `fc` test carries `fc` and not `spade`, so `scripts\test.ps1` and the Docker leg (`-L spade -LE gpu`) leave it out with no script edit. An `fc` test that cannot find the autopilot image fails (`TD-5`); it may skip only for the named absence "no autopilot image", and the skip is reported by name and does not count toward green on the development box (`TD-13`'s reading).

**What these tests cannot show.** A repeat test shows reproducibility, not correctness (`01-verification.md`, "What a determinism test cannot see"). A flight that holds 5 m shows that PX4 flies the model Spade built. It does not show that the model is the real X500; that is phase 6, against flight logs. The run report says the flight controller's own compute is not modelled (the map, piece 1), and a test asserts the report says so (check K9).

**Who writes which test.** The merged sections split the tests between the realms; the bars are held here whoever writes the test.

| Test | Written by | Notes |
|---|---|---|
| FC-U1 messages, FC-U2 frames | Interface (their section 7.3) | the bars below are what I hold them to |
| FC-U3 sensor statistics | Physics ("each term is its own test") | same |
| The fake-peer lockstep test (10,000 periods, a silent peer, a stale reply) | Interface, in the ordinary suite | calls the same gap checker as FC-L1 |
| `fc_host --replay` and its unit test | Core (the first test of their phase 1) | FC-R1's pinned golden and the leg's reproduction are mine |
| FC-B budget-mode tests | Core (their phase 2 list has the too-slow-board RED test) | I review against the bars and own the leg's reproduction |
| FC-L1, FC-F1, FC-R2, the mutation set, FC-M, the run-folder checker, the `fc` label, `scripts/fc-run.ps1` | Test/Docs | |

**Settled by the merged sections** (these replace my phase 0 assumptions A1 to A4):

- **S1. The tick and the link step.** Physics proposed and Core took `dt` = 500 us with one substep. PX4's period is 4 ms, which is 8 ticks; ArduPilot's 2.5 ms is 5. A *link step* is one sensor period, 8 ticks for PX4. The periods in ticks: IMU 8, barometer (50 Hz) 40, magnetometer (100 Hz) 20, GNSS (10 Hz) 200. 500 us stays a proposal until Physics' convergence check passes (hover and an attitude step against 250 us). My bars count link steps, so they hold at 250 us too (16 ticks). In lockstep the reply to exchange k is applied during period k+1, so **one sensor period of delay, 4 ms, is in every loop**.
- **S2. Frames.** Physics' table: (N, E, D) = (x, z, -y), for vectors, axial vectors and a quaternion's vector part (a proper rotation, determinant +1), and the same for the body, (F, R, Dn) = (x, z, -y). Interface owns the code. The vectors in FC-U2 agree with theirs.
- **S3. The trace and the record.** Core's: `trace.bin` is one record per tick (tick, truth, the applied command, each new sample) with a rolling hash and a final `trace_hash`; `commands.bin` is the command stream as applied; `manifest.yaml` holds a SHA-256 for every file. My phase 0 idea of one record per link step with message hashes is dropped. **"Bit-equal at every step" now means `trace.bin` equal byte for byte**, and the test names the first differing tick.
- **S4. The PX4 link.** Spade listens on TCP 4560 and PX4 connects out (from its container, through Docker Desktop's host alias). v1.17.0 is pinned. PX4 has no lockstep timeout of its own, so the link carries one (5 s by default, the named refusal `px4_no_reply`). Still open until phase 1's first measurement: the number of replies per sensor message (the link's rule is exactly one, or it refuses by name), that the default SITL build is lockstep, and the sensor rates PX4 accepts. v1.17.0 can rarely deadlock in lockstep; v1.18 fixes it.
- **S5. Grades** (Core, section 3.4 and 3.5). The replay (FC-R1) and the budget-mode tests (FC-B) are `reference`: integer arithmetic and a golden. A live autopilot flight is `best-effort` until FC-R2 shows it repeatable, and a measured-mode run is `best-effort`. `open(..., min_grade)` refuses a run below the minimum, so a gate that wants `reference` refuses a flight and never downgrades it. The flight bars are properties, not goldens.
- **S6. No host checkpoint** (the lead's ruling in phase 0): the autopilot restarts for every episode, and simulated time restarts at zero. A run is one fresh PX4 container.

## 1. Test cycles and pass bars

### Phase 1: PX4 flies the X500, no Kat

#### FC-U1. Messages (unit, `spade`; written by Interface, bars held here)

- **Golden vectors, one per message the link sends or reads:** HEARTBEAT, HIL_SENSOR, HIL_GPS, HIL_ACTUATOR_CONTROLS, and the few the harness uses to command the flight (COMMAND_LONG for arm, take-off and land; COMMAND_ACK; the landed-state report).
- **Bar:** `encode(decode(v)) == v` byte for byte for every vector, including MAVLink v2's truncation of trailing zero bytes and the CRC with its per-message extra byte. `decode(encode(m)) == m` for 1,000 seeded random messages per type, floats compared by bits (a NaN payload survives).
- **Refusals, each named and each its own case:** bad magic, bad CRC, length that disagrees with the header, a truncated frame, an unknown message id with a good CRC (skipped and counted, never an error), a length over the maximum.
- **RED first:** each decode case is written against a stub that returns "no message", and each refusal case against a corrupted vector, so every case is seen to fail before it passes.
- **Where the vectors come from (`TD-4`):** not from our encoder. The recommendation is bytes captured from the real PX4 container in phase 1, which PX4 itself sent and accepted, pinned with their provenance (release, command, date). The alternative is a reference generator (pymavlink at a pinned version), which is a download for Cameron's OK. The per-message CRC extra bytes come from the message definitions in PX4's own tree, once, after the PX4 fetch the map already lists.

#### FC-U2. Frame conversions (unit, `spade`; written by Interface, bars held here)

- **A signed-permutation conversion is exact.** Position, velocity, force and the body axes between Spade's y-up world and NED and FRD are signed permutations of the components, which floating point does exactly. **Bar: bit-equal**, for the 24 proper rotations of the cube applied to the attitude and for the three axis vectors each. A conversion that is not a permutation (a motor's install turn that is not a multiple of 90°) is within 2 ulp.
- **Meaning vectors, derived by hand, not by the conversion code:**
  - level at rest: the accelerometer reads +g up, which in FRD is `zacc = -g` (`-9.80665 m/s²`), `xacc = yacc = 0`;
  - pitched nose up 90°: `xacc = +g`;
  - rolled right wing down 90°: `yacc = -g`;
  - turning counter-clockwise seen from above at ω: `zgyro = -ω` (a turn about up is a turn about down with the sign reversed).
- **Bar on the vectors:** within 1e-6 relative at fp32. These agree with Physics' table of six rates (a roll rate about the forward axis stays; turning left, gyro `(0, 0.2, 0)`, becomes `(0, 0, -0.2)`; nose-up pitch rate `(0, 0, 0.3)` becomes `(0, 0.3, 0)`) and with Interface's list: each map's determinant, level-at-rest accelerometer `(0, 0, -g)`, a 90-degree yaw, pitch and roll, the quaternion round trip.
- **The unit changes the link adds are not permutations,** so they are not exact: pressure from pascal to hectopascal, the field from tesla to gauss, velocity to centimetres a second with the `int16` clamp (327.67 m/s; beyond it is refused by name, Interface's rule). **Bar: within 2 ulp, and the clamp case refuses.**
- **GNSS origin.** Spade's GNSS has no datum (`03-sensors.md`), so the link owns the origin. The conversion to degrees times 1e7 and back stays within 1.2 cm (a half step of 1e-7 degree is 0.56 cm) over ±5 km, against a double-precision reference written in the test. The projection PX4 uses is recalled, so a vector pins it once phase 1 reads the source.

#### FC-U3. Sensor statistics (unit, `spade`; the sensors and their tests are Physics', the bars are held here)

Every sensor is run alone, on a body at rest, so a million samples take seconds, and **every case has a pinned seed**, so a pass is a pass for ever and nothing flakes. The bars come from sampling theory and are fixed now:

| Sensor | What is checked | Bar |
|---|---|---|
| IMU gyro and accelerometer (exist) | sample mean; sample standard deviation; Allan deviation at three averaging times against the closed form for the row's noise density and bias walk; the density scaling (run at 250 Hz and at 500 Hz: the Allan deviation at the same averaging time is the same); **the turn-on bias** (one seeded draw per run from N(0, σ_on), Physics' new term): the same seed gives the same offset twice, and across 1,000 seeds the draws have mean within 5σ_on/√1000 and deviation within 11% (5/√2000) | mean within 5σ/√N of the bias; deviation within 5/√(2N) relative (±0.8% at N = 200,000); Allan within 10% of the closed form at N = 1e6 |
| GNSS (exists) | the Gauss-Markov bias: stationary deviation and lag-1 autocorrelation `e^(-dt/τ)`; the white part | deviation within 5%; autocorrelation within ±0.02; N = 100,000 fixes (sensor-only, so cheap) |
| Barometer (new) | pressure against the International Standard Atmosphere table at 8 altitudes, noise off; the noise deviation; the Gauss-Markov bias (stationary deviation and lag-1 autocorrelation, as the GNSS) | within 0.1 Pa (about 1 cm); the other two as the IMU and GNSS |
| Magnetometer (new) | the world's field rotated into the body at 24 attitudes: its length, and its direction against hand vectors; the noise and the Gauss-Markov bias; a hard-iron offset when the row declares one | length within 1e-6 relative; direction as FC-U2; noise as the IMU |
| All | the sample count over 100 s (200,000 ticks) is exactly 25,000 IMU, 5,000 barometer, 10,000 magnetometer and 1,000 GNSS samples (a sensor sample is never shed under load, `03-sensors.md`); the same seed gives byte-equal samples; two sensors' noise streams are uncorrelated (|ρ| < 5/√N); the GPU backend's draws sit inside `CORE-3`'s band | exact; exact; as stated; as `CORE-3` |

The barometer and magnetometer tests are written first and fail as `absent:` until Physics' rows land (`TD-5`). Physics' barometer takes its power law from `fp32_math` (`TD-3`, their commit `9db2fc7e`); the reference table is in double and independent of it.

#### FC-L1. The link test (`fc`)

- **What runs:** 10,000 lockstep link steps (40 s of simulated time) against PX4 at its pinned release, with the X500 at rest on the ground, noise on, armed or not. Resting contact works today, and the velocity it reports at rest, -g times dt (-4.9 mm/s at 500 us, `PHY-8`), is a named limit and far under PX4's landed-detection thresholds (Physics, section 5.3).
- **A gap is any of these, and one fails the test:**
  - a link step with no sensor message sent, or two;
  - a link step whose actuator reply did not arrive before the next step began (Spade never advances before the reply; the link's own wait is 5 s by default, and its named refusal is `px4_no_reply`, Interface's);
  - a count of replies per sensor message other than exactly one (Interface's rule: one, or the link refuses by name; phase 1's first measurement may change it, and this bullet follows what is recorded);
  - a sample of any sensor sent twice, lost or out of order. The magnetometer's 10 ms period is 2.5 exchanges, so its sample goes in the first exchange after it is due, up to 2 ms late, once (Physics' section 1.4 may instead move it to 125 or 50 Hz);
  - a simulated time that does not advance by exactly the step (4,000 µs, 8 ticks) between consecutive messages;
  - in the PX4 log, a `sensor_combined` timestamp difference other than the step *(to be checked against the pinned release, S4)*;
  - a count of sensor messages that differs from the count of steps, in the trace or in PX4's own log.
- **One gap checker, one site (`TD-9`).** A function over the link's report (steps, replies per sensor message, wall wait, last `time_usec`: Interface's section 7.1) and the trace. Interface's fake-peer test in the ordinary suite and this test call the same function, so the 10,000-period bar is one bar met against a fake peer and then against PX4.
- **Fault cases, each RED first:** the autopilot stopped mid-run (the container paused): Spade does not advance, and the test fails with `px4_no_reply` at the link's timeout, never a hang. The autopilot killed: named refusal. A malformed reply: skipped and counted as in FC-U1, and the run fails if the count is above zero.
- **The rare lockstep deadlock.** v1.17.0 can rarely deadlock (v1.18 fixes it), and it would show here as `px4_no_reply`. That is a failure, reported by name. The soak measures how often it happens, and whether to rerun once or re-pin v1.18 is decided on that figure, not before (question 4).
- **Soak, nightly:** 250,000 steps (1,000 s), same bars.

#### FC-F1. The scripted flight (`fc`)

The script: arm, take off to 5 m, hold 60 s, land, disarm. No wind. It runs twice: **F1a with every noise model off**, which isolates the link and the conversions (and matches PX4's own Gazebo reference, whose IMU, barometer and magnetometer carry no noise, so Physics asks that the first flight run with the noise rows at zero), and **F1b with the X500's default sensor models on**, which is the flight that counts. A failure of F1b alone points at the noise or the estimator; a failure of both points at the link.

**Which model.** Physics' **PX4-match variant** (PX4's own x500 numbers: mass 2.0643 kg, its inertia, thrust constant and rotor time constants of 0.0125 s up and 0.025 s down) is the link's validation: if Spade flying PX4 with PX4's own numbers misbehaves, the link or a frame is wrong, not the model. The **kit model** (1.63 kg, one rotor time constant of 0.0761 s, three to six times PX4's lag) is flown next with the same bars, and may need airframe parameter changes. A failure on the kit model alone is a finding about the model, recorded as one, not a link failure. The variant gates from its first pass; the kit model is reported until it has passed once, and then gates (question 5).

**Ground contact is a dependency.** The kit model has no landing legs and a contact proxy of 0.377 m, so it would stand 0.377 m off the ground (Physics, section 5.3). Until Physics' feet exist, F1 can start only from an elevated spawn, and the bar that the body touches the ground only before take-off and after landing waits for them.

The map's bars hold, and I refine them in three places:

1. **Altitude is judged on Spade's truth, not the autopilot's estimate (`TD-4`).** An estimate that is wrong by 5 m (a barometer bias) would hold its own altitude perfectly and pass a test that reads the estimate. So:
   - **Truth within ±0.3 m of 5 m for the whole hold** (the map's bar, kept).
   - **The autopilot's estimated altitude within 0.3 m of truth** across the hold: this is the check that catches a wrong sensor.
2. **The hold window is defined.** It starts at the first step after the truth has stayed inside ±0.3 m of 5 m for 2 s, and lasts 60 s. Take-off must reach that point within 20 s of the command, or the flight fails as "never reached the hold".
3. **More than altitude.** My a-priori additions, which the map does not have and which review should confirm:
   - horizontal position within ±1.0 m of where the hold began;
   - speed under 0.5 m/s and tilt under 5° in the hold;
   - touchdown vertical speed at or under 1.0 m/s, and the autopilot reports disarmed within 10 s of touchdown;
   - Spade's invariants hold throughout (no NaN, no body inside a solid), and the body touches the ground only before take-off and after landing (once the feet exist).

**"No estimator failsafe" and "a clean PX4 log", made checkable:**
- the log's failsafe flags are clear at every sample **from a 5 s settle window on, except a headless allow-list of four** (`auto_mission_missing`, `offboard_control_signal_lost`, `manual_control_signal_lost`, `gcs_connection_lost`: the harness loads no mission, sends no offboard stream and attaches no remote control or ground station), each with its reason beside it in the checker, checked per flag so a flag on no list fails by its name (the lead, 2026-11-23);
- the estimator's innovation test ratios stay under 1 **from the same 5 s settle window on** (start-up values are printed, not judged);
- no log message at ERROR level or above, except entries on a short **allow-list that starts empty**, each entry added with its reason beside it (as a band's margin is, `TD-2`).

**Phase-1 flights cost** *(estimate)*: 25,000 link steps, about 100 s of simulated time.

#### FC-R1 and FC-R2. The repeat tests

The map's one test hides two questions: is *Spade* repeatable, and is *PX4 in lockstep* repeatable? If PX4 changes one output by one bit, Spade's trace differs, and that is not a Spade failure. So:

- **FC-R1, Spade's replay (`spade`, no autopilot).** Core's `fc_host --replay <run>` loads `commands.bin` and steps the same world with the same seed and no autopilot; it must reproduce `trace_hash` exactly, and `trace.bin` byte for byte. Core writes the replay and its first test. What I add is the golden: a seeded, generated command stream (hover trim plus a seeded perturbation) replayed in the ordinary suite, with the final `trace_hash` **pinned under `TD-1`**, and **the Docker gcc leg must reproduce it (`TD-12`)**. This is the strong claim and it is cheap: it puts the Spade side of every link under both toolchains with no autopilot.
- **FC-R2, the live repeat (`fc`).** The same seed twice, each in its own process and its own fresh container (S6). **Bar: `trace.bin` is identical byte for byte.** The test also writes `repeat-diff.md`: the first differing tick, and the PX4 log differences by topic and first differing timestamp, apart from fields on a reasoned wall-clock or process-id allow-list. Per S5 a live run is `best-effort` until this passes.
- **If PX4 turns out not to repeat**, the bar becomes bands on the hold's statistics (mean and spread of altitude, horizontal drift, estimator innovations), measured over 20 repeats and then pinned with margin (`TD-2`). That decision is recorded after the measurement and is not made now.

### Phase 2: the Kat package on the simulated companion computer, budget mode

Spade builds the board profiles and the compute model (Core's section 3); Kat's `kat_deploy` is what runs on it. Core writes these tests, and the bars on Spade's side are:

- **FC-B1. The arithmetic is integer nanoseconds** (Core, section 3.2). A component takes its `cost_ns` divided by the board's `speed.factor` (work per second here over work per second on the reference box, so a larger factor is a faster board), and a stage takes the longest of its components. The chain's latency `L` is the sum of its stages plus the link's fixed latency and `8 * bytes / rate_bps` each way. Nothing reads a clock, so the same seed gives the same count on every toolchain. The rounding rule is stated once and the tests pin it.
- **FC-B2. Overruns, RED first.** One stage, sensor period `P` = 4 ms (8 ticks), cost `L`. A command is released at `t + L` rounded up to the next tick (and to the next `output_hz` slot), and an overrun is `L` over the deadline, which defaults to `P`:
  - `L` = 2 ms: no overrun, the command is released exactly 4 ticks after;
  - `L` = 2 ms + 1 ns: no overrun, released 5 ticks after (rounded up);
  - `L` = `P` exactly: no overrun (the boundary is "over", not "at");
  - `L` = `P` + 1 ns: an overrun at every delivery;
  - `L` = 6 ms (1.5 `P`): by Core's rule 4 (samples that arrive while the chain is busy are skipped and the newest is delivered at release), one overrun and one skipped sample in every two periods. This follows my reading of that rule and is checked against Core's text before the test is written.
  - Each expected count is worked out by arithmetic in the test from the profile (`TD-4`), not read from the meter, and each case is written to fail against a model that adds no latency.
- **FC-B3. The speed factor scales exactly.** At twice the factor every cost halves, within 1 ns of rounding.
- **FC-B4. A too-slow profile trips the package's failsafe** (the map's bar, RED first): the meters show misses, the failsafe trips, and the tick where it trips is the same in every run.
- **FC-B5. The same seed gives the same outputs, trace and overrun count**, bit-equal, and the Linux leg reproduces the overrun count (`TD-12`). The flight bars of F1b are re-run through a package: the 6-gate course (exact state, then estimated state) and the hover box.
- **FC-B6. The meters are present and recounted.** `meters.yaml` holds overruns, late and skipped samples, latency statistics per stage (min, mean, p99, max, in ns) and, in measured mode, the memory peak. They are finite, and the overrun count equals a recount from the per-tick costs in the run folder (check K6).
- **FC-B7. No clock outside the two places that may read one.** A source scan, in the manner of `M1B.FixedStepNoWallClockSymbolsInEngineSource`, finds no wall-clock symbol under `tools/fc_host` except in `measured/` and in `fc_host_calibrate`, the only places Core's section 3 allows. RED first by a seeded clock call in `budget/`.

### Phase 3: measured mode, job-object caps

Results here vary, so **no test pins a measured number**. The bars are properties, each with a margin, and every figure printed carries its box and tree (`TD-8`). Measured mode is `best-effort` (Core, section 3.4) and waits for phase 2 to pass and for Kat's REALTIME runtime.

- **FC-M1. The CPU rate cap holds.** This is Core's own first test of the phase: spin a known load under a cap and report what the cap delivers. A busy child under a 10% cap uses 7% to 13% of the wall time over five 10 s windows (the median), measured on this box *(the width is an estimate; the first measurement fixes it under `TD-2`)*.
- **FC-M2. Affinity holds.** A child with four busy threads and two cores used never exceeds 2.1 cores of CPU time per second of wall time.
- **FC-M3. A memory cap below the package's peak is a named refusal.** The host reports `memory_cap_exceeded`, naming the cap and the peak, writes the run record, and stays up. A crash of the host fails the test.
- **FC-M4. Starvation trips the failsafe, and ample does not.** At a cap at or under half of what the package needs, the failsafe trips in 20 of 20 runs. At twice what it needs, it trips in 0 of 20. The middle is not tested, since a boundary case is flaky by nature. Both counts are reported with the spread of the trip time.
- **FC-M5. A measured run replays exactly.** The host records the commands it applied with their ticks (Core, section 3.3), so check K11 holds for a measured run: replaying `commands.bin` reproduces its `trace_hash`.

### Phase 4: scenarios at scale

Gusts, sensor noise and bias, GPS loss, link loss and latency, battery sag, compute starvation, as nightly sweeps. A flight that ends in a landing is not a failure of a GPS-loss run, so a sweep's bar is not "every flight passes":

- **Each scenario declares its expected outcomes** (for GPS loss: the autopilot reports the failsafe within a stated time, then lands or holds, by the scenario's setting). An outcome outside the set is red; one inside it is data.
- **The sweep passes** when every run folder passes the checks of section 3, every run's trace reproduces for a 10% sample re-run, and the sweep's summary lists every run's manifest hash. Spade does not sign (the lead, O144): the manifest is what Kat signs from phase 2.
- **Scale is bounded by cores, not by Spade.** PX4 is one process per drone, and every episode is a fresh container (S6), so a sweep pays PX4's start on each run and its parallelism is the box's 16 threads, shared with Kat's tree, not the 256 worlds the Vulkan record measures. Sweeps are sequential or a handful wide *(estimate)*.

### Phase 5: ArduPilot through the same seam

FC-L1, FC-F1, FC-R1 and FC-R2 are rerun against it with their bars unchanged, at its 2.5 ms period (5 ticks) and over its JSON link on UDP 9002 (Spade listens; ArduPilot sends first). FC-B and FC-M do not depend on the autopilot and are not rerun. **One bar changes, and Interface's and Physics' reading of its documentation confirms it:** ArduPilot's simulator link takes truth for position, velocity and attitude and makes its own GPS, barometer and compass, so only Spade's IMU reaches it. The barometer, magnetometer and GNSS tests of FC-U3 stay, but ArduPilot flights exercise the IMU and the link alone, and the estimated-versus-truth bar of F1 tests ArduPilot's own sensors, not Spade's.

### Mutation set: the flights, RED first

A test that cannot fail proves nothing, and a real flight cannot be made to fail by editing the test. So the flight tests are shown red by breaking the *input*:

| Mutation | What the test must report |
|---|---|
| two motor outputs swapped in the index table, with the link's open-time check bypassed (the check itself, which refuses a mismatch by name, is Interface's test) | F1 fails (never reaches the hold, or flips) |
| a barometer bias of 5 m | F1b fails on the estimated-versus-truth bar |
| one gyro axis sign flipped in the conversion | F1 fails |
| the autopilot's reply delayed by one more step (a period of delay is already in every loop, S1) | L1 reports the gap |

Run nightly, not per gate, because each is a flight.
